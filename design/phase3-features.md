## P3.0 Facts the design leans on (checked against the tree at `d93345a`)

**The engine and the bot already carry the hooks** (Phase 0 Stage A, ported in Phases 1-2):
- **Negotiations are the chat model.** Every history entry has a `seq` and a message; `open` requires a message and refuses a second open chat between the same pair and more than the ruleset's opens per pair per turn (`crates/citar-engine/src/game/diplomacy/negotiation.rs:279-326`). Opening is an own-turn action (`any_time: false`, `api/tools/registry.rs:899-916`); answering is any-time. `accept/counter/reply/reject` with `decline/withdraw/end` read as `reject` (`negotiation.rs:400-409`); an empty counter is refused (`:556-564`); the message cap (`max_chat_messages`, the game's `config.diplomacy` or the ruleset's 30) closes a chat as `expired` instead of taking the message (`:568-571, 630-645`). The `end_turn` tool refuses while any negotiation the player is in is open, naming the one to answer first (`end_turn_refusal`, `:800-824`); `Game::end_turn` keeps the safety net that expires the initiator's chats (stage E0, `:776-793`). `close_negotiation` is exposed (`EngineGame.close_negotiation`, `citar/_facade_rust.py:874-879`).
- **The model-facing text was rewritten in Phase 0.** The registry no longer promises an immediate reply (`registry.rs:899-940, 1024-1031`) and `turn_progress` already lists the open negotiations and says `end_turn` waits for them (`api/briefing/mod.rs:742-756`). One gap remains: `respond_negotiation`'s schema lists only `negotiation_id` and `action` as required (`registry.rs:928`) although the engine refuses an entry without a message.
- **Seats.** `Controller` has `Hybrid`; `Handicap` (`human|ai`) and `AutoDecisions` (`un_vote`, `conquest`, `free_picks`) are separate, with defaults derived from the controller (`state/players.rs:59-129`). `EngineGame.set_controller(pid, controller, handicap, auto)` (`_facade_rust.py:951-955`) and the lobby's per-seat `handicap`/`auto` (`citar/server/session.py:1489-1492`) reach them.
- **The drive knows hybrid seats.** `Game::drive` stops with `Stop::HybridDiplomat(pid)` once a hybrid seat's driver has played, and the next drive ends the turn (`game/turn/drive.rs:152-155, 324-329`); a driver's `respond` may return `DriverOutcome::Deferred`, which leaves the chat to the host and makes that seat's end of turn wait (`Stop::AwaitingReply`, `:59-75, 449-468`); "the next drive asks the driver again, so a host whose wait has run out has the bot decide by driving with a driver that answers this time" (`:67-73`). `Game::answer(pid, nid, driver)` puts one chat to a driver (`:352-381`).
- **The bot's switches and advice.** `citar_bot::Owners` maps the ten categories (`trades, agreements, peace, war, denounce, un, city_states, espionage, captured_cities, chat`; `game/diplomacy/category.rs`) to `bot|llm` and decides `owns(negotiation)` (`crates/citar-bot/src/owners.rs`). `citar_bot::advice()` returns `{deal_value, war_readiness, spare_luxuries, wants}` (`lib.rs:334`); `citar_bot::evaluate()` values arbitrary terms (`lib.rs:350`) but is **not bound to Python**. The facade has `bot_instance`, `bot_set_diplomacy`, `bot_owns_negotiation`, `EngineGame.drive`, `.answer`, `.bot_advice` (`_facade_rust.py:344-390, 962-1028`).
- **Scenarios** list `hybrid` among their seat types (`api/scenario/editor.rs:24`), but `normalize_seats` keeps only the `llm` and `bot` sub-objects of a seat (`editor.rs:203-213`).
- **The client view** has no explored-region, era-stage or home-continent block (`api/views/client.rs:118-139`); the map keeps a continent per tile (`state/map.rs:41, 58`).

**The server today:**
- `SEAT_TYPES = ("human", "mcp", "llm", "bot")` (`session.py:23`). `BotAgent.play_turn` drives a `hybrid_diplomat` stop straight on, since no session has hybrid seats yet (`citar/agents/bot_agent.py:70-73`), and waits at most `REPLY_WAIT_SECONDS = 90` per turn for other seats' answers (`:25, 65-91`). `LLMAgent` gives each message it sends `negotiation_wait_seconds = 240` (`citar/agents/llm_agent.py:123, 394-467`).
- **Responders:** after every action, `_dispatch_negotiation_interrupts` starts one daemon thread per `(negotiation, entries)` for bot and LLM seats; the `_responding` set is never pruned (`session.py:362-402`); an unanswered chat is rejected with "(no response)" (`:404-417`). `LLMAgent.respond_negotiation` opens a fresh conversation per exchange, with the full system prompt, 15 tools and no deadline (`llm_agent.py:634-691`).
- **Model calls:** a worker's `busy` refusal makes `_step` sleep and retry forever, metering a request each time (`llm_agent.py:204-222, 259-266`); `WorkerConversation` ignores the helper's `Done.duration` and its `close()` does nothing (`citar/agents/providers/worker_provider.py:91-142`); `WorkerHub.submit` refuses at once when the connection's `in_flight >= max_concurrent` (`citar/server/workers.py:212-247`). Report narratives call the SDKs directly, outside `make_conversation`, and poll a busy worker every 5 s for up to 30 minutes (`citar/reports/__init__.py:387-444`).
- **Occupancy is per activity:** `pool.seats.occupied()` counts every live game with a living LLM seat on a machine for the whole game, plus named claims (`citar/pool/seats.py:36-63`); probe runs and reports claim a machine for their whole run (`citar/probes.py:631`, `reports/__init__.py:309`); benchmarks count `occupied` against `max_parallel` (`citar/server/benchmarks.py:776-826`); quiet hours and make-way pauses look only at `seat.type == "llm"` (`session.py:599-704`).
- **Admission** runs only at game creation and tolerates `concurrency` (`pool/seats.py:200-218`); `update_seat` skips it (`citar/server/app.py:569-582`); `PURPOSES = game, benchmark, probe, scenario, lab` (`citar/pool/admission.py:32`); `budgets.reserve/settle/release/refresh_from_ledger` have no caller outside `tests/test_pool.py`.
- **Two registries:** `config/servers.json` (`citar/servers.py`), dialled directly, edited by admin-only routes (`citar/server/admin_api.py:45-293`) and the `#/servers` page (`citar/web/js/servers.js`); and DB `servers` rows reached through helpers (`citar/server/pool_api.py`, `#/pool`, `citar/web/js/pool.js`). Three concurrency numbers: `Server.max_concurrent`, `config.connection.max_parallel`, the helper's `hello.max_concurrent`. A helper's hello overwrites `config.hardware` and replaces the model list (`workers.py:329-361`).
- **The usage ledger** is JSONL with no user (`citar/usage.py:1-17`); `session_servers` charges every LLM seat's machine as held for the whole game (`usage.py:277-295`).
- **The database** has the 16 tables of revision `f064316a6b34` plus `767c824c2fcb` (`citar/db/models.py`, `citar/migrations/versions/`). Visibility is `private|allowlist|link|public` and the string is compared in `models.py:276`, `auth/access.py:21-37, 164-183, 280-293, 310`, `server/app.py:514`, `pool/__init__.py:43`, `server/ownership.py:166`, `server/share_api.py:60-62`. `User.public()` exposes `role` and `status` (`models.py:171-183`). Users have no bio, links or field visibility. `ownership.sync` is never called and the engine's phase is `playing|over`, so a finished game keeps counting against `max_concurrent_games` (`app.py:185-202`, `ownership.py:58-72`). Nothing writes a `reports` row. Benchmark suites and runs, probes, lab experiments, scenarios and maps have no owner, and their routes need only `require_user` (`app.py:785-1424`); any member can change any queue priority (`app.py:1389-1410`); bot profiles and lab experiments are admin-only (`citar/server/bots_api.py`). Model scores read every save whatever its `data_sharing` (`citar/server/scoring.py:87-115`).
- **The web client:** Diplomacy is a modal rebuilt from `get_diplomacy` on every negotiation event, which wipes the textarea and the deal builder (`citar/web/js/panels.js:704-824`, `game.js:248-257, 315-324`); the minimap is a 200x130 canvas of the whole map, not aspect-correct, with the explored tiles drawn where they are (`game.js:58-72, 998-1030`); the nav has no people or profile pages (`nav.js:6-9`).
- **Tests and checks:** 665 Python tests (141 s); `scripts/audit_routes.py --strict` counts 190 routes, 0 unguarded; test.yml's front-end job parses every module as ESM; `scripts/dev_server.py` defaults to port 8799 (the owner's) and `scripts/server_soak.py` shows how a script refuses it. `tests/__init__.py` writes `TEST_REGISTRY` (a host, a dry-run machine, a dry-run "GPU box", an Anthropic API row, an electricity plan) as the suite's `config/servers.json`, which the benchmark, costing, pool and server-drive suites read through `servers.py`.

**Where the server acts for whoever asks** (found by the design review, each checked at `d93345a`):
- **A seat's model block is trusted.** Without a `server_id`, `servers.resolve_llm` returns the seat's `llm` block unchanged (`citar/servers.py:750-751`) and `pool_seats.authorize` skips it (`pool/seats.py:211`); the OpenAI and Anthropic providers then dial its `base_url` with the key named by its `api_key_env`, or with the server's own `OPENAI_API_KEY`/`ANTHROPIC_API_KEY` (`agents/providers/openai_provider.py:34-38`, `anthropic_provider.py:24-32`). `create_game` and `update_seat` take the block from any member (`app.py:505-529, 570-582`; `update_seat` runs no admission at all), and a scenario's seats keep it minus `api_key` (`api/scenario/editor.rs:203-212`).

- **The hub forgets a request once it is resolved.** `submit`'s timeout resolves the request and sends `CANCEL` (`workers.py:237-243`), and a frame for a resolved id is dropped (`:128-135`), so `in_flight` falls while a v1 helper is still generating.

- **`LLMAgent`'s clock** leaves reconnects and pauses out of the turn's time (`_waited`) but counts chat waits against it (`llm_agent.py:401-467, 523`), and sets the request's timeout before the call goes out (`:185-188`).
- **Admission** refuses `concurrency` when the `in_flight` it is given reaches the grant's `concurrency` or the machine's slots (`pool/admission.py:240-253`).
- **The game's debug route** takes named actions only (`meet_all`, `reveal`, `gold`; `app.py:688-705`).

## P3.1 Goals, non-goals and exit

### P3.1.1 What Phase 3 delivers

1. **3A Accounts.** A fresh Alembic baseline; the visibility ladder `private | allowlist | link | server | global`; an owner and a visibility for every job type; profiles with per-field visibility and avatars; a members-only directory; an admin users page with the audit log; the legacy server registry merged into the Servers page.
2. **3C The prompt scheduler.** One scheduler per machine for every provider: full leases (a model playing every turn) and partial tickets (one prompt), priority, FIFO and round-robin across members, loaded-model-only pooled work, cancellation, generation-time metering. Task classes in admission; the Queue page's pooled prompts.
3. **3B The compute ledger.** `compute_events`, credits per hardware class, hourly rollups, given and used per member with self-use excluded, budgets that finally reserve and settle, the ratio on profiles.
4. **3E Trade chat.** Lobby timeouts enforced by the session, status events for the two parties, one model conversation per chat, the late-reply fix; a docked chat window per civilization with the deal builder inside.
5. **3D Hybrid seats.** A bot plays the turns and a model does the diplomacy categories the seat hands it; triggers, a 3-minute diplomat phase, the bot's veto on mixed deals, fallback to the bot; lobby, scenario, benchmark and probe support; the diplomacy leaderboard.
6. **3F The minimap.** It follows explored land only, by era, keeps its size, never shrinks, and is aspect-correct.
7. **3G Machine settings.** A dialog per machine: capabilities (LLM slots, model swaps, CPU limits for Phase 4), auto/manual hardware, models and power with the last scan kept, the hardware class, the trust tier.
8. **Phase 2's handoffs** (P3.5.8): `replay.js` decodes the `Delta` replay format and `Full` is retired; views answer with an ETag; trade options are fetched when the deal builder opens instead of riding in every view.
9. **Closing the paths where the server acts for whoever asks** (P3.0's last list): members' model blocks name a machine row (P3.2.9), the machine routes that touch the host stay admin-only (P3.2.8), and a revoked or disabled machine is disconnected.

### P3.1.2 Owner decisions that bind this phase

From the plan (§1) and the owner's instructions for Phase 3:
- **Hybrid:** every diplomacy category is a per-seat bot/LLM toggle; the model is prompted on events plus every N turns (default 10); difficulty is chosen per seat; an optional advisor, off in benchmarks; a separate diplomacy leaderboard from paired seeds.
- **Pooling:** full and partial task classes; pooled prompts may run between a lobby game's turns, never while a benchmark game holds the machine; pooled prompts only on loaded models unless the machine's owner allows swaps; speed metrics use generation time, never queue wait.
- **Chat:** a docked, non-modal window per civilization that pops up at once; strict turn-taking with a thinking/queued indicator; End Turn waits for a reply with a timeout (a model's reply 10 min including queue time, an AI waiting on a person 5 min, both lobby settings), then a hybrid seat falls back to its bot and a full model seat declines; a cap of 30 messages; bots answer with canned lines.
- **Minimap:** human seats only; explored land only; at most 44x28 early, the explored home continent from the Renaissance, the full map from the Information era; keeps its size, never zooms back in.
- **Accounts:** visibility `global` means the public web, keeping allowlist and link sharing; profiles with per-field visibility, a 256 KB avatar upload, a members-only directory with an opt-out, an admin users page; future restrictions are capability flags.
- **Ratio:** GPU generation-seconds plus CPU core-seconds plus a credit priced per hardware class; self-use excluded; the member chooses who sees it, admins always can.
- **General:** there are no users yet, so schema and data may break (a fresh Alembic baseline); stability and speed first; fix bugs rather than carry them; one agent at a time; never port 8799, `C:/dev/citar-play`, a push or the VPS.

### P3.1.3 Non-goals

- **Phase 4:** the Rust helper and protocol v2 (raw completions, a real cancel, settings and catalog frames, power reports), CPU jobs and their limits, proof of work, the automatic trust tiers, the Rust hardware scan. Phase 3 must not depend on any of it, and leaves these hooks (named in each section): the machine's `capabilities.cpu` and settings, `compute_events.kind = 'cpu'` with `verification`, hardware classes for CPUs, `trust_tier` on users and machines, scheduler capacity read from one settings function, and the cancel path `Conversation.close() -> hub.cancel()`.
- **Phase 5-6:** packaging, deploy, the release docs pass, the real-model hybrid soak (plan §4.8).
- Federation between CITAR servers; streaming completions (protocol v1's unused `CHUNK`).

### P3.1.5 What changed since the plan was written

Each checked against the code at `d93345a`:
1. **3E's engine half is done.** Sequence numbers, required messages, the cap, the aliases, the empty-counter refusal, the End Turn rule, `close_negotiation`, the tool text and the chat lines in `turn_progress` are all in the Rust engine. What is left in the engine is the schema's `required` list (P3.5.4).
2. **The "late reply" defect has changed shape.** A person's reply to a model's offer is no longer lost at the end of the model's turn (the turn cannot end with the chat open), but a reply that comes after the tool's own wait reaches the model only when it tries `end_turn` or asks `get_diplomacy`. The fix is to put the reply in front of the model before its next step (P3.5.3).
3. **The hybrid turn is the engine's drive.** The plan's "bot plays with LLM-owned categories off, the lock is released, the diplomat runs, the turn ends" is `drive()` → `Stop::HybridDiplomat` → the diplomat outside the lock → `drive()` again (P3.6.3). `BasicBot.diplomacy_owners` is citar-bot's `Owners` on the bot handle.
4. **"Engine changes in Python first" happened, in Rust.** Phase 3's Rust changes are small: `respond_negotiation`'s schema (3-11); `replay_data(Full)` retired and `trade_options` moved out of the per-refresh view into its own call (3-13); a binding for `citar_bot::evaluate` and `normalize_seats` keeping a seat's `hybrid` object (3-14); and the minimap block in seat views (3-17).
5. **The registry merge is a storage move, not only a page merge.** `servers.py` (LLM seats, managed model loading, quiet hours, keys), benchmarks, costing and reports all read `config/servers.json`; it moves into the `servers` table (P3.2.8).
6. **Budgets were in money** (`budgets.currency`, priced by `costing.py`). They become credits, the ledger's unit, so they can reserve and settle against `compute_events` (P3.4.6).
7. **`public` becomes `global`,** and `server` is new; the string sweep covers every place P3.0 lists.
8. **"Helpers report power"** needs protocol v2's `power` frame: Phase 4. Phase 3 keeps the host's own power sampler and the JSONL power rows Phase 4 will write into.
9. **The plan's 'server' pseudo-user** is `provider_id = NULL` (and `consumer_id = NULL` for the server's own data collection), so no fake account appears in the directory or the admin page.
10. **Saves:** seats are saved with the session record (`asdict(seat)`, `session.py:888-893`), so a seat's `hybrid` block needs no save-format change; the engine needs none either.
11. **Report narratives** bypass `make_conversation` today; they move onto it so that the scheduler sees every model call (P3.3.4).
12. **The plan's defect list is not all fixed.** "Revoking a token doesn't disconnect the helper" (plan §2) still holds, and neither Phase 3's first draft nor plan §6.7 covered it; it is fixed in the registry merge (P3.2.8). The review also found the open paths of P3.0's last list, which the plan did not name: a member's seat can make the server dial any address with any of its environment variables as the key, and several machine routes act on the host.
13. **Phase 2 left three items to Phase 3** (P3.0): the `Delta` replay in `replay.js`, view ETags and trade options on demand. They are Phase 3 work (P3.5.8), not non-goals.

### P3.2.2 The schema baseline

- **One revision replaces both.** `citar/migrations/versions/` loses `f064316a6b34` and `767c824c2fcb` and gains `0016a_baseline` (down-revision none), written by hand from the metadata and checked by a test that compares it with `Base.metadata` (alembic's `compare_metadata` finds nothing). A later package that must change the schema adds a revision on top, with an upgrade test from the baseline; nothing re-squashes.
- **Old databases.** `server/boot.py:migrate()` today runs `upgrade head`, or `create_all` plus `stamp head` for tables without `alembic_version`. It gains:
  - a database at `f064316a6b34` or `767c824c2fcb` (a 0.1.5 or Phase 0-2 database): on SQLite, the WAL is checkpointed (`PRAGMA wal_checkpoint(TRUNCATE)`), the engine is disposed, the file and any `-wal`/`-shm` left are **renamed** (never deleted) to `citar-0.1.5-<YYYYmmdd-HHMMSS>.db` beside it, a warning names the new path, and the server starts on a fresh database. If a rename fails (on Windows, another process holding the file), the server **refuses to start**, naming the file and the error; it never carries on with the old database or with half of it renamed (a rename that failed part-way is undone before the refusal). On Postgres it refuses to start with a message saying to create a new database (`CITAR_DB_URL`) or drop the schema, since a server process should not rename someone's database;
  - any other revision the scripts do not know (a newer build's): refuse to start, as today's alembic error, with the message spelled out;
  - tables without `alembic_version` (only tests create those, with `db.create_all()`): `stamp head` only if `users.listed` exists (the baseline's), otherwise treated as an old database.
  - Saves are not in the database: a game loaded from disk gets its `games` row again (`ownership.register_existing`, now called on load).
- **Tables and columns** (`citar/db/models.py`):

### P3.2.5 The games index

`ownership.sync(sdb, session)` runs from the session (off the game lock, through `ownership.sync_quietly`, on the writer's thread after an autosave lands, so it costs no lock time) when the phase or the turn changes and when a session stops: `status = "playing"` while `phase == "playing"`, `"finished"` once it is `over` (with `finished_at`), `"closed"` when a running game is closed without finishing, `"playing"` again when it is loaded.
- **The game limit** counts rows with `kind = "game"` in `setup` or `playing` only: a member's benchmark and probe games are the run's, limited by the benchmark and probe queues, not by the lobby's two games.
- **No row stays "playing" without a game.** At boot, after `restore_live`, every row in `setup` or `playing` with no live session (a failed restore, a deleted save folder, a crash between registration and the first save) is marked `closed`, with a log line per row.
- **`GameSession.owner_id`** is set from the game's row wherever a session comes to life: the create and load routes, `SessionManager._register_loaded`, `restore_live`, and the benchmark and probe runners (from the run's owner). The scheduler and the ledger read it; a session without one is the server's own (P3.4.2).

### P3.2.6 Profiles and the directory

- **Field visibility.** `users.field_visibility` holds `{profile, display_name, avatar, bio, links, items, ratio}`, each `private|server|global`. Defaults: `profile`, `display_name`, `avatar`, `bio`, `links`, `items` = `server`; `ratio` = `private`. A field shows when the viewer's level reaches both the field's and `profile`'s: anonymous visitors see `global`, members `server` and `global`, the owner and admins everything. The handle is always shown wherever the account appears (seats, sharing, grants). Setting a field to `global` is refused on probation ("New accounts can show their profile to members only").
- **`User.public(viewer)`** returns `id`, `handle`, and `display_name` and `avatar` (the upload's route or the sign-in picture) **only when those fields are visible to `viewer`** under the rule above; otherwise `display_name` is the handle and `avatar` is null. `role` and `status` move to `User.account()` (the owner's own view and admins). The viewer is passed at every call site: `shared_with`, grant subjects, server owners, seat owners (seat lists of `global` games are read by anonymous visitors), the directory, the Queue page and the admin pages. A test lists the callers (`git grep "\.public("` over `citar/` against a fixed list), so a new caller without a viewer fails.
- **Search** in the directory matches the handle, and the display name only for accounts whose `display_name` is visible to the caller, so a hidden name is never revealed by its hits.
- **Avatars.** `POST /api/auth/me/avatar` (multipart, at most 256 KB) accepts PNG, JPEG and WebP, recognised by their magic bytes and with dimensions read from the header (PNG IHDR; JPEG SOFn; WebP VP8, VP8L, VP8X), at most 1024x1024; anything else is refused with the rule. Stored as `<data dir>/avatars/<user id>-<sha256[:12]>.<ext>` (the previous file removed), never under the code or the saves. `GET /api/users/{handle}/avatar` serves it with the type fixed by the validated format, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and a cache lifetime, when the `avatar` field is visible to the caller; else 404. `DELETE /api/auth/me/avatar`. No image library is added: nothing is decoded, only the header is read.
- **`PUT /api/auth/me`** also takes `bio` (control characters stripped, 1,000 characters), `links` (at most 3; label up to 40 characters; `http`/`https` URLs up to 300 characters), `field_visibility` (known keys, known values) and `listed`.
- **`GET /api/users`** (members only): accounts with `listed` and an active status, newest first, searchable by handle or display name, each with the fields visible to the caller; paged by 50.
- **`GET /api/users/{handle}`** (anyone): 404 unless `profile` is visible to the caller; the visible fields; the account's items visible to the caller (games rows and owned items, through `visible_filter` with `owner_id = them`, 20 per kind, newest first) when `items` is visible; the ratio block when `ratio` is (3-10). A hidden account (not `listed`) still has a page for whoever may see it; it is only missing from the directory.

### P3.2.8 The registry merge

- **Every machine is a `servers` row.** `servers.py` keeps its public functions (`find`, `get`, `list_servers`, `host`, `resolve_llm`, `seat_ref`, `describe_seat`, `model_entry`, `profile`, `ensure_model`, `restricted_now`, `restricted_text`, `server_name`, `normalize_server`) with their return shapes, and reads and writes rows instead of `config/servers.json`: a row's `config` already holds the `normalize_server()` dict (`pool/__init__.py`), and `reach` says who dials (`direct`: CITAR; `worker`: the helper). `with_pooled()` becomes the identity. The electricity plans move to `settings_kv` (`electricity_plans`); `host_server_id` becomes the row with `is_host`.
- **One-time import.** When `config/servers.json` exists and `settings_kv.registry_imported` is unset, `pool.import_registry` brings every server in **under its own id** (so seats, suites, saved games, the usage ledger and the keystore entries keep resolving), in no group (sharing one is a later choice of its owner), owned by the first admin (in local mode, the local owner), `reach = direct`, `is_host` for the registry's host, `server_resource` for the host and for `api` kinds; then it sets `registry_imported` and renames the file `servers.json.imported-<date>`. API keys stay in the keystore under the same ids. A fresh server-mode database has no admin at boot, so the import runs at boot when an admin exists, and again from `accounts.on_first_admin()` (P3.2.4) once something makes the first one; until then `servers.py` reads nothing (no machine is usable) and the boot log says why. `POST /api/pool/import-registry` (`pool_api.py:572`) is retired.
- **One concurrency number.** `Server.max_concurrent` is the site's LLM slots; `config.connection.max_parallel` is read once on import and dropped from new configs (`normalize_server` keeps reading it as an alias). The helper's `hello.max_concurrent` is its local ceiling, and the scheduler takes the smaller (P3.3.2).
- **Routes, each with its own gate.** `admin_api.py`'s routes keep their paths; owner-or-admin means MANAGE on the row (`access.on(Server)`); "direct or host" means the row has `reach = direct` (admin-only to create, below) or `is_host`. A member's helper row is never dialled by the server and never reaches the host's LM Studio: its models come from its helper's hello, and a host-touching route on it answers 404, without spawning `lms`, loading the SDK or sending a request.

### P3.2.9 Model blocks from members

A seat's `llm` block decides which address the server dials and which key it sends, so a member may only **name a machine**, never describe one:
- **`servers.member_llm(block, user) -> dict`** is the one gate. For a non-admin it keeps `server_id`, `model`, `model_id`, `profile_id` and the `SEAT_OVERRIDES` keys, and drops everything else (`provider`, `base_url`, `api_key`, `api_key_env`, `timeout`, unknown keys). The `server_id` must resolve to a row the member may use (P3.3.7 admits it); a block without one is refused (400, "Pick a machine for this seat") unless its `provider` is `dryrun`, which dials nothing. Until the registry merge (3-05) a machine of `config/servers.json` is not a row, and `pool_seats.authorize` skips it today, so a member could spend the host's GPU or the site's API key with no grant: from 3-01 such a machine is refused for non-admins unless its provider is `dryrun` (403, "only an administrator can seat this machine until it is shared"), and from 3-05 every machine is a row and admission decides. Admins (and the local owner, who is an admin) keep inline blocks, which is how tests and scripts give a raw provider.
- **Its callers:** `create_game` and `update_seat` (which now also runs `pool_seats.authorize` on the new block), the scenario editor's save and `/api/scenarios/{id}/launch` (a scenario saved by an admin with an inline block launches for a member only after the block names a machine), benchmark suites' model entries and probe subjects (both already name machines; the gate refuses anything more).

## P3.3 3C: the prompt scheduler, task classes and the Queue page

### P3.3.1 Today

Every model call goes straight to its provider. A helper machine answers `busy` when its slots are full and the caller sleeps and retries; a direct machine has no slot accounting at all. Machines are "occupied" per activity for a whole game. There is no per-request queue, fairness or priority; `pool.queue` orders whole jobs (benchmark jobs, probe runs, reports, lobby games' make-way) by priority and age (`citar/pool/queue.py`). See P3.0.

### P3.3.2 Machines and capacity

- **`citar/pool/scheduler.py`** keeps one `Machine` per `servers.id`, made on first use and shared by the whole process: sessions, the benchmark scheduler, the probe runner and the report runner. The lab never calls models.
- **Capacity** is `Server.max_concurrent` (the one site number, P3.2.8), capped by the connected helper's `hello.max_concurrent` for a helper machine. While a helper machine is offline its capacity is unknown: lease requests pass through, so the provider's connection error drives today's reconnect window and disconnect policy, and tickets are refused as temporary. A **disabled** row refuses every lease request and ticket ("this machine is disabled"), and its helper has been dropped (P3.2.8).
- **Not scheduled:** a model configuration without a `server_id` passes through, measured by the metrics but not by the ledger. Only an admin's inline block or a session with no owner (tests, scripts) can have one; a member's cannot (P3.2.9).
- Capacity, the loaded models (a helper's reported `loaded` flags; LM Studio's model list for a direct LM Studio machine, cached; every model for an online API) and the quiet hours are cached per machine, re-read at most every 5 s and at once on a helper's connect or disconnect, so no request touches the database.

### P3.3.3 Leases, tickets and the order

- **A lease** (task class *full*) is a model seat that plays every turn, and it **belongs to the session's seat, not to its agent** (agents are made lazily, at the seat's first model turn, and a lease made with them would leave a machine looking free while a game that will want it is loaded, restored, paused or waiting on its bots). `GameSession` makes a lease for every living full seat with a `server_id` when the session is registered: created, loaded (registered paused), brought back by `restore_live`, reloaded by a benchmark, launched from a scenario, or started as a probe's turn case. It releases it when the seat changes type or machine (`update_seat` releases the old lease and makes the new one), the seat is eliminated, the game is over, closed or stopped, or the session crashes. A make-way pause (`pause_reason.kind == "queue"`) releases its leases and the resume makes them again, as `occupied()` skips such games today; every other pause (a person's, quiet hours, a budget, a disconnect) keeps them, since the game resumes where it left off. The agent binds to its seat's lease (`GameSession.lease_for(pid)`), which outlives it. Kinds: `game` (a lobby game; lends its slot while idle), `benchmark` (never lends), `probe_case` (a probe's turn case, for the case only; never lends). Every request the seat makes, in its turn or answering a chat out of turn, is a request of its lease.
- **Active and idle.** A lease is *active* while its seat is mid-turn and *idle* (lending, for a `game` lease) otherwise. The driver calls `activate()` before the seat's `play_turn` and `idle()` after it. The agent also calls `idle()` whenever its turn is blocked on something other than the machine (waiting for a chat reply in `_await_answer` or `_end_turn`, held by a pause) and `activate()` before its next step: a seat waiting on a counterpart must not keep the slot that counterpart needs to answer, which on a one-slot home GPU serving both would otherwise be every such chat.
- **A ticket** (task class *partial*) is one pooled prompt: a hybrid seat's diplomat phase or chat answer, a probe's offer or message case, a report's narrative, the Servers page's test. It carries the machine, model, activity, the consumer (a user id), its class (`chat`, `diplomat`, `probe`, `report`, `test`), a priority, a deadline (the latest start), `steps` (how many consecutive calls it may make once started; default 8) and `wait_for_benchmark`.
- **The rules,** which tests hold as invariants:
  1. Requests in flight, draining ones included (below), never exceed capacity.
  2. Lease requests are served in arrival order and before any ticket: a slot that frees goes to the oldest waiting lease request (skipping one whose consumer is at its grant's cap, P3.3.7), and to a ticket only when no lease request waits.
  3. A ticket starts only when (a) no benchmark lease is live on the machine and no benchmark drain is under way (otherwise it is refused at once, "held by a benchmark", unless `wait_for_benchmark`, when it waits); (b) its model is loaded, or the machine allows swaps (`capabilities.llm.allow_swaps`, P3.8), or a live lease uses that model (otherwise refused at once, "the model is not loaded"); (c) the machine is outside its quiet hours (otherwise refused as temporary, with `retry_at`); (d) its consumer is under its grant's concurrency (P3.3.7); (e) in flight + 1 ≤ capacity − reserved, where *reserved* counts the leases that are active or never lend, and have no request in flight.
  4. **The reservation keeps slots from tickets only.** A lease request may take any free slot, so between an active seat's steps another seat's lease request (its chat answer, its turn in another game) may take the slot, and the active seat then waits its turn in arrival order; a ticket never takes it. A benchmark's slot is never lent to a ticket.
  5. **Borrowing is bounded.** A ticket that starts while a `game` lease on the machine is idle borrows that lease's slot: it runs under its class's cap (`diplomat` 180 s, `chat` 120 s, `probe` 120 s, `report` 300 s, `test` 30 s from its start, and each step's `max_tokens` at most the class's cap), after which its next step is refused and its caller falls back or finishes. So a lobby seat whose turn comes waits for at most one capped step, and that wait is its `queue_s`.
- **Order among tickets:** priority, highest first; within a priority, round-robin across consumers (the one served longest ago first); within a consumer, first come first served. Priority = the class's base (`test` 30, `chat` 20, `diplomat` 10, `probe` 0, `report` −10) + the activity's queue priority (−100..100, `pool.queue.priority`, which its owner or an admin sets on the Queue page).
- **A started ticket** holds its slot for up to `steps` calls (and, borrowing, its class's cap) or until it is closed. States: `queued → running → done`, or `cancelled`, `expired` (not started by its deadline; the caller falls back), `refused` (rule 3, admission or a budget). A running ticket is never cut off by its start deadline: its caller's own budget stops further steps.
- **The benchmark drain.** When a benchmark lease becomes live on a machine, queued tickets that do not wait for benchmarks are refused ("held by a benchmark"), running tickets are cancelled (their callers fall back), and the lease's first request waits until no ticket request is in flight there, draining ones included, for at most `benchmark_drain_seconds` (default 120). The wait is the job's `drain_s` metric; if the bound is reached, the request goes ahead and the job's timing is marked `contaminated` in its result (shown on the run page, left out of the speed score). So no pooled request overlaps a benchmark step. (Lobby leases beside a benchmark are the job-level rule's business, P3.3.5, as today.)
- **Cancel and draining:** a queued ticket leaves the queue; a running one closes its conversation. `WorkerConversation.close()` now calls `hub.cancel(server_id, request_id)`, which sends `CANCEL` and ends the caller's wait with an error; on a direct machine the HTTP call is abandoned (closing the connection, which LM Studio and the online APIs stop on). A v1 helper ignores `CANCEL` and keeps generating (Phase 4 fixes that), so the scheduler keeps that request's slot as **draining** until the hub sees the request id's late `Done` or error, or its request timeout plus the hub's 15 s grace passes. The hub hands frames for resolved ids to the scheduler (`scheduler.late_frame(server_id, request_id)`) instead of dropping them (`workers.py:128-135`), and `submit`'s own timeout drains the same way. The scheduler's in-flight count is therefore the helper's own, and the hub has no reason to refuse `busy`.
- **A `busy` refusal anyway** (a helper restarted with fewer slots, an accounting bug) is never retried blindly: the scheduler lowers the machine's capacity to its in-flight count until the next frame frees a slot, puts the request back at the head of its queue, and logs the mismatch; the request then waits on the machine's condition like any other, with no sleep and nothing metered.
- **Position and ETA:** each machine keeps an exponentially weighted mean of generation time per (model, class); a ticket's ETA is the expected time of the work ahead of it over the slots it may use. Both are published to the ticket's status callback.

### P3.3.4 The conversation wrapper and metering

- `make_conversation(cfg, system, tools, binding=None)`: with a lease or a ticket and a scheduled machine it returns `ScheduledConversation(inner, binding)`, whose `step()` acquires the binding's slot (blocking; never with a session lock held, P3.3.9), sets the inner conversation's request timeout only then (from the caller's remaining budget, which the queue does not shorten), runs the inner step, releases, and records `last_gen_s` and `last_queue_s`.
- **Generation time is bounded by what the server saw.** On a helper machine `gen_s = min(Done.duration, observed)`, where *observed* is the server's wall time from sending the request frame to receiving its `Done` (`WorkerConversation` now keeps both); on a direct machine it is the wall time of the HTTP call after the slot was granted. Both values travel in the step event and in `compute_events` (P3.4.2). Token counts are capped at the request's `max_tokens` (output and reasoning) and at the model's context length (input). A helper whose reported duration exceeds the observed time by more than 10% plus a second on three requests within an hour gets `flags.overreports` on its machine row, an audit row and a note on the admin's view of the Servers page; Phase 4's trust tiers can read it. A modified helper therefore cannot raise its owner's given credits beyond the time the server actually waited for it.
- **Listeners:** `scheduler.add_listener(fn)` receives a `StepEvent` (machine, model, activity, consumer, task class, class, `gen_s`, the reported and observed seconds, `queue_s`, the usage delta, request id, time) after every step. The usage tracker's `llm()` is the first listener and replaces `LLMAgent._meter`, so an attempt that never reached the model meters nothing; the ledger is the second (P3.4).
- **One path for every model call.** Report narratives (`reports.complete`, which today calls the SDKs directly) and the Servers page's test go through `make_conversation` with a ticket; `_complete_on_worker`'s polling goes.
- `LLMAgent._step` loses its `busy` branch. `metrics.model_step` records `gen_s` as the step's seconds and a new `queue_s`; the stats screen shows "waited for the machine" beside generation time, and the model score's speed reads generation time only.
- **The turn's clock counts the model's own time only.** Each step's `queue_s` and every chat wait (`_await_answer`, `_end_turn`, and from 3-11 the clock-bounded waits of P3.5.2) are added to `LLMAgent._waited`, as reconnects and pauses already are, so neither counts against `max_turn_seconds` (1800); the request timeout `_step` gives the call is set after the slot is granted, from the turn's remaining time. A turn with 25 minutes of queueing and chat waits and a minute of generation ends by `end_turn`, not `time_limit`.
- `WorkerHub.submit` keeps its busy check as a safety net only.

### P3.3.5 Occupancy, quiet hours and the job queue

- `pool.seats.occupied()` returns the labels of the leases live on a machine (game, benchmark, probe case). Since leases belong to registered sessions' seats (P3.3.3), a game loaded paused, restored, or whose bots move first is listed, as today's `occupied()` lists it. Hybrid seats, chat answers and report narratives are tickets and never occupy a machine. `claim()` and `release()` go.
- `pool.queue` stays the job-level queue for work that needs a lease (benchmark jobs, probe runs, lobby games making way). Reports leave it: their narrative is a ticket. A benchmark job starts when its machine has fewer leases than its limit (`scheduler.leases(server_id)`); the benchmark scheduler also counts its own running hybrid jobs, which hold no lease (P3.6.9), against that limit, and never starts a hybrid job on a machine where a benchmark lease is live. A probe run takes a `probe_case` lease for each turn case and tickets for offer and message cases; a lobby game's `_quiet_hours` and `_make_way` apply to its full seats.
- `usage.session_servers` counts a machine as held by a game only while one of the game's leases is live on it.

### P3.3.6 Lending and the benchmark rule

A lobby lease lends its slot while its seat is idle (between its turns, and while it waits on a chat or a pause), within the borrowing caps of P3.3.3 (P3.1.2). A benchmark lease never lends; when one becomes live the machine drains its pooled requests first, and while one is live no ticket starts there, so no pooled prompt shares the GPU with a benchmark step (P3.3.3's drain). A hybrid benchmark game holds no lease: its prompts are tickets with `wait_for_benchmark` and no start deadline (P3.6.9), and the benchmark scheduler keeps hybrid and full jobs of its own off each other's machines (P3.3.5), so it never runs beside a full benchmark and never stops pooled work.

### P3.3.7 Admission and task classes

- Grant purposes gain `pooled` (partial prompts); `game` remains full seats; an empty list still means all.
- Capabilities `full_llm` and `partial_llm` (P3.2.4) are the hooks for future restrictions (plan A3). An LLM seat needs `full_llm` and a grant for `game`; a hybrid seat `partial_llm` and `pooled`; a report's narrative `run_reports` and `pooled`; a probe run `run_probes`, with `probe` for its turn cases and `pooled` for the rest.
- `pool_seats.authorize` checks every seat with a model by its class, and `update_seat` runs it again.
- **Admission decides who may, the scheduler when.** Leases and tickets are admitted with `admission.check(..., in_flight=None)`, which checks the grant, the purpose, the window and the budget and skips the capacity step, so a busy machine queues the work rather than refusing it. A ticket is admitted when it is made (`purpose="pooled"` for the consumer on that machine); a refusal is the ticket's `refused`, with the admission's reason and `retry_at`. An offline helper still refuses a ticket at once (`online=False`).
- **A grant's `concurrency`** (`AccessGrant.concurrency`, 0 meaning no cap below the machine's slots) is enforced by the scheduler as a cap on that consumer's running requests on the machine, leases and tickets together (rule 2's skip and rule 3(d)). The baseline keeps the column.

### P3.3.8 The Queue page

- `GET /api/queue` lists **only the machines the caller may view** (`access.on` on the `Server` row: its owner, members its groups reach, admins), and adds a single line "n other machines are busy" for the rest, with no names or loads; today it names every machine to every member. Per machine it adds its capacity, its leases (activity label, kind, lending or active, the member when the caller may see the activity) and its running and waiting tickets (position, class, the activity's label or "someone's <class>" when the caller may not see it, the member's handle under the same rule, model, priority, waited, ETA, deadline).
- `POST /api/queue/priority` takes `kind = game|benchmark|probe|report|lab` and needs MANAGE on the activity (P3.2.4); tickets follow their activity's priority. `POST /api/queue/tickets/{id}/cancel` (new) is for the activity's owner, the machine's owner and admins.
- `citar/web/js/queue.js` shows a "Pooled prompts" section under each machine, with priority buttons and cancel only where the caller may use them.

### P3.3.9 Threading

One lock and one condition per machine. `acquire` waits on the condition in ticks of at most a second, to notice cancellation, a stopped session and its deadline. The callers are threads already (the session driver, responders, the report and probe runners, benchmark sessions). Nothing in the scheduler takes a session lock or reads the database on the request path.
- **Only `acquire` blocks.** In test mode `acquire` asserts that the calling thread holds no session lock (sessions register their `RLock` in a weak set when `CITAR_TEST_LOCKS` is set, and an `RLock` can tell whether the calling thread owns it). `cancel`, `release`, `idle`, `activate`, `close` and the late-frame and status bookkeeping take the machine lock only to update counters, never wait, and are allowed under a session lock: `suspend`, `update_seat` and `_crashed` cancel agents there, and the chat clock cancels answers there.
- **Callbacks run outside the machine lock.** Status callbacks (`queued`, `thinking`, the Queue page's counts) are queued while the machine lock is held and delivered after it is released, by one notifier thread per process, so a callback that takes a session lock can never meet a thread that holds that session lock and waits for the machine lock.

### P3.3.10 Phase 4 hooks

Capacity and the swap rule come from one function, `servers.machine_settings(server_id)`, which Phase 4's settings frame will also feed; every request carries the id the v2 `cancel` frame will name; v2's reported `gen_s` arrives through the same listener.

## P3.4 3B: the compute ledger and the ratio

### P3.4.1 Today

The usage ledger (`citar/usage.py`) is JSONL in `saves/usage/`, per activity and machine, with held, busy and CPU seconds and tokens, and no user; `costing.py` prices it by reading every file. Budgets never accrue. Nothing records compute given or used per member.

### P3.4.2 `compute_events`

| Column | Meaning |
|---|---|
| `id` | integer, autoincrement |
| `at` | when the work ended (UTC, indexed) |
| `activity` | `game:<id>`, `benchmark_run:<id>`, `probe_run:<id>`, `report:<id>`, `lab:<name>`, `test:<id>` (indexed) |
| `activity_kind` | `game`, `benchmark`, `probe`, `report`, `lab`, `test` |
| `task_class` | `full`, `partial`, `cpu` |
| `consumer_id` | the member whose activity it is (FK users, SET NULL, indexed); null for the server's own data collection |
| `provider_id` | the machine's owner (FK users, SET NULL, indexed); null when the server provides the machine |
| `machine_id` | `servers.id` (indexed) |
| `kind` | `gpu`, `cpu`, `api` |
| `model` | the model that served it, or null |
| `gen_s`, `cpu_core_s` | generation seconds (bounded by what the server observed, P3.3.4); CPU core-seconds |
| `reported_s`, `observed_s` | for a helper's model step: the helper's `Done.duration` and the server's own wall time from request to `Done`; null otherwise |
| `tokens_in`, `tokens_out`, `tokens_reasoning` | from the provider's usage, capped as P3.3.4 says |
| `credits` | priced at write time (P3.4.3) |
| `flags` | JSON: `overreported`, `capped_tokens`, `unpriced` (an `api` step whose model has no token price) |
| `self_use` | true when consumer and provider are the same member, or both are the server |
| `verification` | `unverified` for model work (attributed, never re-run; plan C2), `verified` for the host's CPU; Phase 4 writes `pending` for helpers' CPU jobs |
| `request_id` | the model request, for audit |

- **The consumer** is the activity's owner: the game's `games.owner_id`, the run's, the probe run's, the report's, the experiment's owned item. It is null when the item is marked `collection` (only admins set it: the server's own benchmarks and data gathering), which counts as given by whoever's machine served it.
- **The provider** is the machine's `owner_id`, or null when the machine is `server_resource` (the host; online APIs the site provides).
- **Given(u)** = events with `provider_id = u` and not `self_use`. **Used(u)** = events with `consumer_id = u` and not `self_use`. So a member's own games on their own GPU count on neither side; another member's hybrid prompts on their GPU count as given; their own games on the server's CPU count as used; work on a server machine for the server's own collection counts on neither.

### P3.4.3 Writers, credits and hardware classes

- **Writers.** (1) The scheduler's listener: one `gpu` (or `api`) event per model step. (2) The host's CPU, **measured per unit of work**: `time.thread_time()` deltas around each drive and engine answer on a game's driver thread, each responder task on the responder pools' threads (which serve many sessions in one window, so sampling them would misattribute), each report build and each probe case; the unit's activity is charged directly, and at each flush the usage tracker hands the ledger one `cpu` event per activity for the window, on the `is_host` machine, `provider_id` null. The 5 s thread sampling (`usage.py:_sample`) stays only for a driver thread's time outside those units (save writes and the like), charged to its session. (3) The lab: each game's `cpu_s` in its result (`lab.py:393`) becomes one `cpu` event, the experiment's owner its consumer. (4) Phase 4: helpers' CPU jobs.
- Events go through a ledger writer thread with a queue, inserted in batches (every 2 s or 200 events), never on a game's lock.
- **Credits** = `gen_s × rate` for `gpu`, `cpu_core_s × rate` for `cpu`, and for `api` the step's **token cost** (`costing.price_tokens` with the model's prices in force, in the registry's currency) `× rate`, with the rate of the machine's class of that kind. The default rates for compute are an energy proxy, one credit for roughly 300 W for a second: an unclassified GPU generation-second 1.0, a CPU core-second 0.05 (about 15 W a core). An online API's default is 1,000 credits per unit of currency, roughly the generation time a home GPU spends producing the output a unit of currency buys from an API, so a member who uses the site's paid key is charged for it in the same unit and an admin's budget on that key has something to count. An `api` step whose model has no price is credited 0 and flagged `unpriced`. Admins edit classes and rates (`/api/admin/hardware-classes`); a new rate applies from then on, and `citar admin reprice --since <date>` recomputes the credits of a period when wanted.
- **A machine's class** is the first class of its kind, by priority, whose `match` fits the machine's hardware (`gpu_name` regex, `vram_gb_min`, `cpu_name` regex, `cores_min`), else the kind's default; it is recomputed when the hardware changes, unless an admin pinned it (`class_override`).

### P3.4.4 Who sees what

- `GET /api/ledger/me?range=24h|7d|30d|all`: given and used (GPU seconds, CPU seconds, credits, tokens), the ratio (given credits over used credits; "only given" when nothing was used), by machine and by activity kind.
- `GET /api/users/{handle}/ratio`: the same totals when the account's `ratio` field is visible to the caller (P3.2.6); admins always.
- The admin users page shows each account's 30-day given, used and ratio; the Account page gets a "Compute" card; a profile shows the ratio line under the field's rule.
- Ratio-based restrictions later: an admission rule may read `ledger.ratio(user)` and set capabilities; nothing does in 0.1.6.

### P3.4.5 Rollups

`compute_rollups(user_id, hour, side, kind)` with sums of `gen_s`, `cpu_core_s`, `credits`, `tokens_in`, `tokens_out` and `events`, keyed by all four. A rollup thread recomputes, every 5 minutes, each hour touched since its last pass (delete and insert per hour, one transaction). Reads use the rollups for complete hours and the raw events for the current hour, so a total never waits for the pass.

### P3.4.6 Budgets

- A grant's budget is in credits per period (day, week, month or total, in the owner's time zone as today), hard or soft.
- **Reserve:** when a lease request or a ticket under a grant with a budget starts, `budgets.reserve(budget, activity, estimate)` holds the machine's mean credits per step for that model (at least 1; on an `api` machine, the cost of the request's `max_tokens` of output plus its input at the model's prices, times the class rate). If a hard budget's spent plus reserved would pass its amount, the request is refused with the period's end as `retry_at`: a lease's game pauses with that reason (as for quiet hours, and resumes by itself when the period turns), a ticket is refused and its caller falls back. A hard budget on an `api` machine whose model has no token price refuses every request ("this model has no price, so its budget cannot be kept"), rather than letting unpriced steps through at 0.
- **Settle:** the ledger's listener settles each step's credits into the entry for (budget, activity, period) and releases the reservation. A soft budget only warns: an event to the consumer and a note on the machine owner's Servers page.
- `budgets.refresh_from_ledger` rebuilds a period's entries from `compute_events`: the admin's repair.

### P3.4.7 What costing reads

`costing.py` keeps pricing each machine by its configuration over time (electricity, depreciation, leases, token prices). Per activity and minute it now reads generation seconds, tokens and the host's CPU seconds from `compute_events`, so queue wait is no longer charged as work; held time and power samples stay in the JSONL ledger, which keeps its activity, `held` and power rows and stops writing `busy`, tokens and requests in spans.

## P3.5 3E: trade chat

### P3.5.1 Today

The engine side is done (P3.0, P3.1.5). The server waits per agent (90 s for a bot's turn, 240 s per model message), starts a thread per responder and gives a model's chat answer a fresh conversation with no deadline. The web client's Diplomacy modal is rebuilt on every event, losing what was typed.

### P3.5.2 Timeouts and the chat clock

- **Lobby settings.** The engine keeps any lobby key verbatim in the game's config (`api/host.rs:270-279`), so no engine change is needed: `chat_model_reply_seconds` (default 600: how long a chat waits on a model seat, LLM, MCP or a hybrid seat's model, queue time included, except behind a benchmark in a benchmark game, below), `chat_person_reply_seconds` (default 300: how long a chat waits on a person), and the existing `diplomacy.max_chat_messages` (default 30). The lobby gets a "Chat" group (minutes, and the cap); `GameSession.info()["config"]` lists them; a game without them uses the defaults.
- **`citar/server/chat.py: ChatClock`**, one per session, started with its driver. It tracks every open negotiation as (entries, awaiting, waiting since, deadline, kind of the awaited seat); a change of entries or of the awaited seat restarts the clock; while the game is paused the clock stands still. It wakes on the session's condition, and at least once a second. At a deadline it first cancels any answer still in progress for that chat (the seat's ticket, or its lease request through the agent's `cancel_chat(nid)`), then acts once, by the awaited seat's kind, through the session (each is an engine call that a lost race turns into an `ActionError`, which it ignores):
  - **a model seat** (llm, mcp): the seat declines, `respond_negotiation(reject, "(no reply in time)")` on its behalf;
  - **a hybrid seat whose model has the chat:** its fallback bot answers (`EngineGame.answer(pid, nid, fallback)`, P3.6.5);
  - **a person:** the chat closes as expired, "(no reply in time)", whoever opened it (an AI waiting on a person declines after the per-game timeout; a person waiting on a person ends the same way);
  - **a bot seat:** never; bots answer inside drives and through their responders at once.
- **Queue time in benchmark games.** In a lobby game the model timeout includes queue time (the owner's rule). In a benchmark session (`session.benchmark`) the clock stands still for a chat whose awaited seat's answer is a ticket queued behind a benchmark lease (the ticket's status says so), and counts only once that ticket has started; so a hybrid benchmark seat whose answer waits out another benchmark is answered by its model, not by the fallback. Every fallback and decline records its cause (`timeout`, `queued_behind_benchmark`, `refused`, `failed`), and the leaderboard leaves out fallbacks not caused by the model (P3.6.10).
- **Deadlines after a restart.** When a session is loaded or brought back by `restore_live`, the clock starts every open chat's deadline afresh from the load; on resume from a pause it carries on from where it stood.
- **The clock is the chat timer, with safety nets.** `BotAgent.play_turn` waits until the chats its drive stopped on move or close; `REPLY_WAIT_SECONDS` (90) goes, and in its place it keeps a safety cap of twice the longest chat timeout of the game, after which it closes those chats as `expired` itself. `LLMAgent._await_answer` and `_end_turn` wait the same way, with the same cap. The clock's loop catches and records every exception (in `session.errors`, `where: chat clock`) and carries on; the driver checks at each turn that the clock thread is alive and restarts it if not, with a log line. The driver's force-end of a turn an agent left open (`_close_open_chats`, `session.py:796-799`) stays as the last resort.
- **An injectable clock.** `ChatClock` and `GameSession._await` take a clock (`time.monotonic` and the condition's wait by default; a fake in tests), so every timeout test runs in fake time and adds nothing to the suite's wall time.

### P3.5.3 Responders

- **`citar/agents/responders.py`:** a queue per (session, seat), so a seat answers one chat at a time, in order, and **two executors** per process. Model answers (an LLM seat's, a hybrid seat's model) run on a bounded pool (`CITAR_RESPONDERS`, default 16); bot answers (a bot seat's, and a hybrid seat's bot-first pass, P3.6.5) are instant engine calls and run on their own small pool (`CITAR_BOT_RESPONDERS`, default 2), so a pool full of model answers waiting for a busy GPU never delays a bot's answer. `_dispatch_negotiation_interrupts` submits `(pid, nid, entries)` there instead of starting a thread; `_responding` drops a key when its chat moves or closes.
- **Cancellation never declines.** `cancel_agent` (a suspension for quiet hours, make-way or a disconnect, a seat change, a crash) halts the seat's responders: a halted responder returns without calling `_reject_if_unanswered` and clears its seat's keys from `_responding`, so the chat waits for the seat's next responder or for the clock. `_reject_if_unanswered` runs only for an answer that ran and failed outright.
- **Dispatch on every return.** On resume, load, `restore_live` and an agent's creation, the session dispatches responders for every open chat waiting on a bot, LLM or hybrid seat, so a chat that was waiting when the game stopped or the seat changed is answered without anyone acting first.
- Bot seats answer as now (`EngineGame.answer`); hybrid seats as P3.6.5.
- **Model seats get one conversation per chat** (`ChatThread`, held by the agent per negotiation, dropped when it closes, rebuilt from the history after a restart). Its system prompt is the diplomacy prompt of P3.5.4 with the seat's persona; its tools are `get_diplomacy`, `get_empire`, `get_players`, `get_victory_status`, `read_notes`, `write_notes`, `log_thought`, `respond_negotiation`, `send_message`. Each exchange adds what changed since the last (the other side's entries, the proposal from the seat's side, the minutes left) and runs up to `max_negotiation_calls` steps on the seat's lease, stopping when the chat moves. `_reject_if_unanswered` stays for an answer that failed outright; a slow one is the clock's.
- **Late replies.** Before each step of its own turn, `LLMAgent.play_turn` compares the chats it is in with the last step's (`_chat_marks`) and adds a note for each that changed, worded by its state, so a model is never told to answer a chat that is closed:
  - waiting on the seat: "NEGOTIATION UPDATE: <name> answered negotiation #n: <their entry>; the proposal from your side: <...>. Answer with respond_negotiation, now or before end_turn.";
  - accepted: "NEGOTIATION UPDATE: <name> accepted negotiation #n: the deal is in effect. No answer is needed.";
  - declined, withdrawn or expired: "NEGOTIATION UPDATE: negotiation #n with <name> is closed (<declined|withdrawn|expired>: <their note>). No answer is needed."
  A person's reply reaches the model at once, not only at `end_turn`.

## P3.6 3D: hybrid seats

### P3.6.1 Today

The engine stops for a hybrid seat's diplomat and lets its bot defer a chat (P3.0); the bot has its switches, its advice and its valuation; the facade can make a bot with owners and drive it. The server has no hybrid seat type, and `BotAgent` drives a `hybrid_diplomat` stop straight on.

### P3.6.2 The seat

```
{"type": "hybrid", "name": "...", (civ_name, nation, leader, color, difficulty as for any seat)
 "handicap": "ai" | "human",                                                   the seat's existing key
 "bot": {"profile": "standard", "aggression": 0.4},
 "llm": {"server_id": "...", "model": "...", "persona": "...", ...},          as an LLM seat's (P3.2.9)
 "hybrid": {"owners": {"trades": "llm", "chat": "llm"} | "trade_only" | "all_but_war" | "everything",
            "advisor": true, "prompt_every": 10}}
```
- **Difficulty and handicap** use the keys every seat already has, which `normalize_seats`, `create_from_scenario` and `set_controller` read: `difficulty` is the level (`set_difficulty`), `handicap` (`ai|human`) is whose numbers the seat plays with. A hybrid seat's `handicap` defaults to `ai`; the lobby labels it "AI bonuses, like the bot" or "a person's values, like a model". There is no third spelling inside `hybrid`.
- **Validation** (`citar/agents/hybrid.py: normalize_hybrid`): owners through `engine_api.bot_set_diplomacy` on a scratch bot (its messages are the errors); at least one category the model's ("a hybrid seat with nothing for its model is a bot seat"); the seat's `handicap` `ai` or `human`; `prompt_every` 1..50 (default 10); `advisor` (default true in lobby games; always false in benchmark games).
- **Presets:** trade only = `trades`, `chat`; all but war = every category but `war`; everything = all ten.
- `Seat` gains `hybrid`; `SEAT_TYPES` gains `hybrid`. Saved with the session record.
- **The engine's seat:** `{"controller": "hybrid", "handicap": seat.handicap or "ai", "auto": {"un_vote": owners.un == "bot", "conquest": owners.captured_cities == "bot", "free_picks": true}}` at creation; `update_seat` and scenario launches call `set_controller` the same way. With `un` the model's, the engine no longer votes for the seat: the model votes with `un_vote`, and a vote it does not cast is an abstention, as for a person. With `captured_cities` the model's, a captured city stays a puppet until the model decides with `city_status`.
- **Scenarios:** `normalize_seats` keeps a seat's `hybrid` object as it keeps `llm` and `bot` (Rust, 3-14).

### P3.6.3 The turn

- **`HybridAgent`** (`citar/agents/hybrid_agent.py`) holds the seat's bot handle (its profile, its owners), a **fallback** handle (the same profile, every category the bot's; both use the seat's one memory in the game, so the fallback carries on the bot's plans), the model's configuration (`servers.resolve_llm`), and the diplomat's state (the last phase's turn and standings, the last event id read, the chats' threads).
- **`play_turn`** (on the driver thread):
  1. under the lock, `session.drive_bots(pid)`, which now drives every seat with a bot (bot and hybrid seats): the bot plays and leaves the model's categories alone;
  2. the drive stops at `hybrid_diplomat` and the lock is let go;
  3. if a trigger fired (P3.6.4) and no phase ran this turn, the diplomat phase (P3.6.6) runs, outside the lock, on one ticket;
  4. under the lock, drive again: the turn ends, or the drive stops at `awaiting_reply` for chats that wait on others (waited for as a bot seat waits, P3.5.2) or on the seat's own model (a chat it deferred, which its responder or the clock's fallback answers).
- Bot seats keep `BotAgent`; only hybrid controllers stop at `hybrid_diplomat`.

### P3.6.4 Triggers

From the events since the last phase and the standings:
- first contact with a major civilization; war declared on the seat; peace made; the seat denounced;
- a deal of the seat's expired or cut (`deal_expired`, `deal_cut`), or ending next turn (from `get_diplomacy`'s until-turns);
- a UN vote open, when `un` is the model's; a city the seat captured, when `captured_cities` is; a city-state event about the seat (`cs_ally_lost`, `cs_meet`, `cs_quest`), when `city_states` is; a `spy` event, when `espionage` is;
- the seat's score, or its military strength against a met civilization, changed by more than 25% since the last phase;
- `prompt_every` turns since the last phase.

At most one phase per turn per seat. A chat that comes in is not a trigger: the responder answers it whenever it comes (P3.6.5).

### P3.6.5 Answering chats

- A chat waiting on a hybrid seat goes to its bot first (inside drives, or `EngineGame.answer` from the responder): the bot answers what it owns and defers the rest.
- A deferred chat (its proposal touches a category of the model's, or it is talk and `chat` is the model's) goes to the seat's model through its responder queue (P3.5.3): a `ChatThread` on a `chat` ticket whose deadline is the clock's, with the diplomat prompt and the chat tools of the model's categories.
- When the ticket is refused or expires, the model's answer fails, or the clock runs out, the fallback bot answers (`EngineGame.answer(pid, nid, fallback)`) and the metrics record a fallback with its cause. On a machine held by a benchmark, the bot therefore answers at once in a lobby game (P3.3.3); in a hybrid benchmark game the ticket waits instead (P3.6.9).
- **One voice per seat at a time.** While a seat's diplomat phase runs, the seat's chat responder holds: chats that come back to the seat during the phase are given to the phase (they appear in its next user message as late replies do, P3.5.3), not to a separate `ChatThread` on its own ticket, which would race the phase's model on the same negotiation. When the phase ends, the responder dispatches whatever is still waiting.

### P3.6.6 The diplomat phase

- **One `diplomat` ticket:** at most 30 s to start (a phase that cannot start soon is skipped and the bot's defaults stand), a 180 s budget once started (the plan's default; the seat's `hybrid.phase_seconds` overrides), at most 8 steps.
- **The system prompt** (`DIPLOMAT_SYSTEM` in `citar/agents/prompts.py`, the same for every call of a seat, so a provider can cache it): "You are the diplomat of {civ} in CITAR, a turn-based strategy game in the style of Civilization V. A scripted bot runs everything else for your civilization: its cities, research, units and the fighting of any war. You decide only these kinds of diplomacy: {the model's categories, one line each}. The bot decides {the bot's categories}. A deal that includes anything the bot decides must be one the bot would accept as a whole: if it would not, your offer or acceptance is refused and you are told why. You are called when something happens (first contact, a declaration of war, a deal running out, a United Nations vote, a large change in strength), every {n} turns, and whenever another civilization talks to you. Each call is short: read what you are given, act with the tools, then stop by answering without a tool call. Every negotiation entry needs a message. You have {model_minutes} minutes to answer a chat that waits on you; the other side has {their_minutes} (a person) or {model_minutes} (another AI) to answer yours, and a chat closes when its time runs out or at {cap} messages. Keep your agreements and suspicions in your notebook (write_notes): it is shown at every call." Then the persona, if any.
- **The user message:** the triggers in words; the diplomatic situation (the seat's `get_diplomacy`, compacted: met civilizations with relations, treaties and their until-turns, open chats, recent messages, the UN); the empire at a glance (`empire_summary`); the notebook's last 2,000 characters; with the advisor on, "THE BOT'S VIEW" (`bot_advice`: deal values in gold from your side, war readiness per rival, spare luxuries, what it would ask for).
- **Tools:** `get_diplomacy`, `get_players`, `get_empire`, `get_victory_status`, `read_notes`, `write_notes`, `log_thought`, and per category the model owns: trades, agreements, peace → `open_negotiation`, `respond_negotiation`; war → `declare_war`; denounce → `denounce`; un → `un_vote`; city_states → `get_city_states`, `city_state_action`; espionage → `get_espionage`, `move_spy`, `stage_coup`; captured_cities → `get_cities`, `city_status`; chat → `send_message`, `respond_negotiation`. The session refuses any other tool the seat's model calls ("That is the bot's to decide.").
- **The veto on mixed deals** (plan 6.1). Before the seat's model opens a negotiation, or answers one with `counter` or `accept`, the session works out the proposal's categories. If any is the bot's, it asks `EngineGame.bot_evaluate(pid, bot, other, give, receive)` (a new binding of `citar_bot::evaluate`, 3-14); a value below zero refuses the call: "The bot decides <categories> and values this deal at <v> gold for you, so it will not agree. Leave those items out, or make the deal better for <civ>." What lies in the model's own categories is the model's to give.
- Tool calls go through `session.call_tool`, taking the lock per call; model calls are outside it.

### P3.6.9 Benchmarks, probes and paired control games

- **Suites:** a scenario gains `mode: "full" | "hybrid"`, and for hybrid `owners` (a preset or a map) and `bot_profile` (default the standard profile). A hybrid job seats the model as a hybrid seat with the advisor off. Its prompts (diplomat phases and chat answers) are tickets with `wait_for_benchmark` and no start deadline, so a phase waits for its slot instead of being skipped after 30 s: a benchmark waits for its model rather than let the bot answer. The chat clock does not count a chat's time while its answer's ticket is queued behind a benchmark lease (P3.5.2), so a wait for another benchmark never turns into a fallback. The clock's model timeout still applies to a model that is reachable but silent once its ticket has started; that fallback is recorded with its cause and counts against the model. The benchmark scheduler counts a running hybrid job against its machine's job limit and never starts one on a machine where a benchmark lease is live (P3.3.5), so a hybrid job's diplomat phases do not sit behind a full benchmark for hours.
- **The paired control game:** every hybrid job has one, with the same configuration and seed and the hybrid seat played by the same bot profile with every category the bot's. The control seat **copies the hybrid seat's `handicap` and difficulty level**, so the pair differs only in who decides the model's categories; its automatic decisions are a bot seat's (the engine votes and annexes for it), since those are the very categories the model takes over in the other arm. Bot-only, it runs headless on the server's CPU (a Python loop over `EngineGame.drive` with the diplomacy recorder), once per (scenario, seed, build id, the bots' fingerprints, the handicap and level), cached in the benchmark directory and shared by every model.
- **Probes:** a probe run gains `mode: "hybrid"` with `owners`. Offer and message cases go to the subject's bot first and to its model when the model owns them, and record which answered; turn cases play the bot's turn, then a diplomat phase with every trigger forced.

### P3.6.10 The diplomacy leaderboard

- **`citar/diplomacy_stats.py: DiplomacyRecorder`** follows one seat through a game's events: proposals made and received; deals made; the acceptance rate of the seat's own proposals; wars declared by and on it; cities captured and lost; peace made; final score, alive, winner. Hybrid sessions attach it to their hybrid seats; control games to the same seat.

An accepted deal keeps the value of the proposal that was accepted.
- A hybrid job's result carries the recorder's rows and its control's id. A pair's line: the score difference (hybrid minus control) at the end and at turns 100, 200 and 300 where reached, deals made, total and mean deal value, acceptance rate, wars and their outcomes.
- **`GET /api/models/diplomacy`** (members): per model and owners preset, the pairs, the mean score difference with a 90% bootstrap interval (2,000 seeded resamples), deals per game, mean deal value, acceptance rate, wars declared per game, captures and losses. Only benchmark pairs count (a lobby game has no control), only runs the caller may see, and pooled data under the minimum-contributor rule (P3.2.4). Fallbacks whose cause is not the model (`queued_behind_benchmark`, `refused`) are listed beside the line and not counted as the model's.
- The Models page gets a "Diplomacy" tab beside the model scores.

## P3.10 Decisions taken in this design

1. **Schema first.** One baseline revision holds every Phase 3 table and column; later packages fill in behaviour, and add a revision only if they must.
2. **Old databases are renamed aside** on SQLite (the WAL checkpointed first; a rename that fails refuses the boot) and refused on Postgres; newer unknown revisions are refused.
3. **The ladder** is `private | allowlist | link | server | global`; `public` is gone; `server` needs no capability; `global` needs `publish_global` (the renamed `publish_public`). **Moderators only unpublish:** `MODERATE` on `global` objects and on `link` objects presented with their slug; every control needs `MANAGE`, which only owners, ACL managers and admins have.
4. **One `owned_items` table** for every file-backed job type, with `games` kept for live sessions and `reports` folded in; ACL entries keyed by kind. A report gathers only what its owner may see.
5. **Capabilities** `run_benchmarks`, `run_probes`, `run_lab`, `edit_bots`, `full_llm`, `partial_llm` join the five; lab and bot editing stay admin-only by default, as today.
6. **Profiles:** per-field visibility with `profile` as the page's own gate; members-only defaults; the ratio private by default; any non-probation member may make their own fields global. `User.public(viewer)` applies the display name's and the avatar's visibility wherever an account appears, and search matches only visible names.
7. **Avatars** are validated by header only (no image library), stored under the data directory, served with a fixed type and a sandboxing CSP.
8. **Members name machines; they never describe them.** A member's model block keeps a `server_id`, a model, a profile and the seat overrides; an inline block (a base URL, a key, a key variable) is an admin's or a dry run's only.
9. **The registry merge** moves `config/servers.json` into the `servers` table behind `servers.py`'s unchanged functions, under the registry's own ids, once an admin exists. Direct-reach machines, `POST /api/llm/models`, and every machine route that touches the host (the hardware scan, LM Studio control, model detection, the `env` key backend, host-wide settings) are admin-only or limited to direct and host rows; a member's helper row is never dialled.
10. **Revoked and disabled machines are dropped** from the hub at once, and the scheduler refuses them.
11. **One LLM-slot number:** `Server.max_concurrent`, capped by the helper's local ceiling.
12. **The scheduler** is in-process, per machine. Leases (full seats) belong to registered sessions' seats; tickets are partial prompts; lease requests are served in arrival order and before tickets; the reservation of active and non-lending leases keeps slots from tickets only; tickets go by priority, then round-robin across members, then FIFO.
13. **Lending:** a lobby lease lends its slot while its seat is idle (between turns, waiting on a chat, paused); a ticket on a borrowed slot runs under its class's cap. A benchmark lease never lends, drains pooled requests before its first step (bounded, with the wait recorded), and while one is live no ticket starts there; tickets fail fast there unless they wait for benchmarks (reports, probes, hybrid benchmark jobs).
14. **Loaded models only** for tickets unless the owner allows swaps, or a live lease uses the model.
15. **Generation time** is the smaller of the helper's `Done.duration` and the server's observed time, or the HTTP call's time after the slot was granted; queue time is recorded apart and never counted as work, nor against a model's turn; token counts are capped; a helper that over-reports is flagged.
16. **A cancel on a v1 helper drains:** the slot stays taken until the late frame or the timeout; a `busy` refusal lowers the machine's capacity and requeues without sleeping.
17. **Admission decides who, the scheduler when:** admission runs without the capacity step; a grant's `concurrency` is the scheduler's per-consumer cap.
18. **Every model call goes through `make_conversation`**, report narratives included.
19. **The ledger:** `compute_events` with consumer and provider, null for the server; self-use (both the same, or both the server) excluded; credits at write time from hardware classes; host CPU measured per unit of work; hourly rollups.
20. **Default rates:** an energy proxy for compute (GPU 1.0 per generation-second, CPU 0.05 per core-second) and an online API's token cost at 1,000 credits per unit of currency; admins edit them.
21. **Budgets are in credits** and reserve and settle per request against the ledger; an API machine's budget is priced from tokens, and a hard budget on an unpriced model refuses.
22. **Costing** reads work from `compute_events` and held time and power from the JSONL ledger.
23. **The chat clock is the chat timer;** lobby keys `chat_model_reply_seconds` (600) and `chat_person_reply_seconds` (300); at a deadline a model declines, a hybrid's bot answers, a person's chat closes as expired. Agents keep a safety cap of twice the longest timeout; the clock survives its own errors and the driver restarts it; in benchmark games it does not count time queued behind a benchmark; every fallback records its cause.
24. **Responders** run on two executors (model answers bounded, bot answers apart) with a queue per seat; a cancelled responder never declines; responders are dispatched again on resume, load, restore and agent creation; a model seat keeps one conversation per chat; a diplomat phase holds its seat's responder.
25. **Late replies** are put in front of the model before its next step, worded by the chat's state.
26. **`negotiation_status`** reaches the two parties and god-view spectators only.
27. **The chat window** is docked left of End Turn (one at a time at 700 px or less) and built on a pure state module tested with `node --test`; drafts and builder state live outside any redraw.
28. **Phase 2's handoffs are Phase 3's:** `replay.js` reads `Delta` and `Full` is retired; views answer with ETags; trade options are fetched on demand.
29. **The hybrid turn** is drive, stop, diplomat outside the lock, drive; a fallback bot handle with every category the bot's answers whatever the model cannot. Its handicap is the seat's existing `handicap` key.
30. **The veto** on mixed deals is the bot's `evaluate()` of the whole deal through a new binding.
31. **One diplomat phase per turn at most,** on triggers and every N turns; 30 s to start, 180 s to run, 8 steps.
32. **The advisor** is on by default in lobby games and always off in benchmark games.
33. **Hybrid benchmark jobs** use tickets that wait for benchmarks and have no start deadline; the benchmark scheduler keeps its hybrid and full jobs off each other's machines; each job has a cached bot-only control game with the same seed, handicap and level.

## P3.11 Risks

1. **Scheduler starvation or deadlock.** Unit tests with a fake clock for every rule, checked as invariants over random schedules; every wait in ticks with a timeout; only `acquire` blocks, and never under a session lock (asserted); callbacks delivered outside the machine lock.
2. **Races between the chat clock and the agents.** The clock acts through engine calls that refuse a chat that has moved; agents only wait, with a safety cap; a cancel never declines.
3. **The registry merge breaking benchmarks, costing or managed loading.** `servers.py` keeps its functions and shapes; the registry's ids are kept; an import fixture test; the test suite runs on a seeded database built by the import; costing tested on a synthetic ledger before and after.
4. **Prompt volume on small GPUs** (KV-cache reuse lost, plan risk 6). A slim, static diplomat prompt; one phase per turn at most; triggers; tickets only on loaded models; borrowing caps.
5. **Ledger write volume on SQLite.** A writer thread with batched inserts; rollups for reads.
6. **Avatar uploads as an attack surface.** Header-checked formats only, a size cap, a fixed served type, `nosniff` and a sandboxing CSP, storage outside the code and saves.
7. **Churn in `game.js` and `panels.js`.** The chat, replay and minimap logic in pure modules with Node tests; the browser checklist.
8. **v1 helpers ignore `CANCEL`.** The scheduler counts a cancelled request's slot as draining until its late frame or its timeout, so capacity stays right; Phase 4 makes cancel real.
9. **The automatic archive of an old database.** Rename only, after a WAL checkpoint, logged with the new path; a failed rename refuses the boot; Postgres refuses; the owner's port-8799 instance gets a fresh database on its first Phase 3 start (its saves on disk are untouched and re-indexed on load).
10. **Members turning the server against its own network or keys.** Closed by P3.2.8 and P3.2.9 in the first and fifth packages, each with tests that patch every outbound path and record nothing.
11. **Self-reported work.** Helpers' generation time is bounded by the server's own observation and over-reporting is flagged; plan C2's attribution holds without trusting the helper's clock.
12. **Nineteen packages in sequence.** Each sized like 2-11 or smaller (three, 3-04, 3-10 and 3-14, at the upper bound, name where to split if they run long), with gates a reviewer can rerun locally, and wall-clock recorded.
