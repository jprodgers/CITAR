## P4.0 Facts the design leans on (checked against the tree at `1d5ca71`)

**The helper today is the Python worker** (`citar/worker/`, about 950 lines):
- **Protocol v1** (`citar/worker/protocol.py`): JSON text frames with `t`, `PROTOCOL_VERSION = 1` (`:39`) matched exactly by the server; worker frames `hello catalog done chunk error pong status`, server frames `welcome request cancel ping shutdown` (`:42-55`); refusals `busy closed unknown_model stopping` (`:59`); an 8 MB frame cap (`:61`). A request carries the whole message list, tools, `tool_mode`, `params`, a timeout and the activity (`:133-144`); `Done` carries text, thinking, parsed tool calls, `stop_reason`, `malformed`, usage and `duration` (`:148-158`). `CHUNK` and `STATUS` are never sent.
- **The agent** (`citar/worker/agent.py`): parses tool calls itself by reusing `OpenAIConversation` with `system=""` and the server's message list pasted in (`:301-341`), so a `json` tool mode's protocol prompt, which only `OpenAIConversation.__init__` appends (`openai_provider.py:44-47`), never reaches the model: the plan's "JSON tool mode is broken through helpers" still holds. Server `params` are whitelisted to `temperature max_tokens reasoning_effort top_p seed` (`:55`) and a configured model list is an enforced allowlist (`:234-243`). `CANCEL` is only logged (`:414-415`). Models are discovered once per connection (`:160-190`) and no catalog frame is ever sent. The hardware scan runs synchronously inside the async session before connecting (`:192-220, 348-353`). Reconnects back off from 2 s to 60 s with 30% jitter (`:47-50, 423-456`); a refused token stops it for good (`:434-440`).
- **Configuration** (`citar/worker/__main__.py`): `--config FILE`, else `helper.json` in the per-user base (`paths._user_base()`: `%LOCALAPPDATA%\CITAR`, `~/Library/Application Support/CITAR`, `$XDG_DATA_HOME/citar` or `~/.local/share/citar`; `CITAR_DATA_DIR` overrides; `:74-77`), a first-run prompt on a TTY that offers to save `helper.json` (`:80-104`), `CITAR_WORKER_*` environment variables, and flags `--server --token --config --base-url --provider --api-key-env --max-concurrent --name --model --quiet --insecure --no-hardware --hardware FILE -v` (`:156-186`); quiet hours as `22:00-06:00` or `Sat 00:00-09:00`, split at midnight (`:38-71`). `citar setup --worker` writes `worker.json` (mode 0600) under the configuration directory and, as root, a system unit `/etc/systemd/system/citar-worker.service` (`citar/wizard/worker.py:150-198`).

**The hub** (`citar/server/workers.py`, the `/ws/worker` route in `citar/server/app.py:2560-2650`):
- One `WorkerConnection` per machine, the newest replacing the older (`workers.py:258-272`); a request bridges from a game thread to the event loop and waits on a `threading.Event` (`:373-413`); `cancel` sends `CANCEL` and ends the caller's wait at once (`:215-229`); frames for resolved ids go to the scheduler as late frames (`:194-213`); `drop` on revoke, disable, delete or suspension sends `shutdown` and closes (`:326-356`); the ping loop checks every connection's token, machine and owner again each round (`:434-468`).
- **Defects found here.** (1) The `worker_auth` rate limit (`ratelimit.py:57`, 20 in 300 s) is recorded only after a failed lookup and its `RateLimited` is swallowed (`app.py:2658-2671`): it never refuses anything, and every attempt costs a token lookup. (2) `request_ip` takes the last `X-Forwarded-For` entry whatever `CITAR_TRUSTED_PROXY_HOPS` and `behind_proxy` say (`app.py:2652-2655`), where the HTTP routes use `ratelimit.client_ip` (`ratelimit.py:174-193`): a client with no proxy in front can choose its own address. (3) `WorkerToken.last_ip` (`models.py:519`) is never written. (4) The version check is exact and comes before authentication (`app.py:2580-2586`), which is right for a refusal that names the version.
- `record_connection` keeps each report as the machine's last report and applies it by its modes (`machine_settings.record_report`, 3-18; `workers.py:554-574`).

**The server's model calls** (`citar/agents/providers/worker_provider.py`): a `WorkerConversation` ships messages and unpacks the helper's parsed `Done` (`:92-161`); `close()` asks the hub to cancel (`:176-184`); the provider's tool-call parsing (native calls, `repair_tool_calls`, XML, GLM, plain text including Gemma 4's own syntax, the JSON protocol) is `openai_provider.py:83-336`.

**The scheduler** (`citar/pool/scheduler.py`) already has every hook P3.3.10 promised: capacity and swaps from `servers.machine_settings` (`:229-244`), the helper's state pushed by the hub (`helper_state`, `:247-262`), every request carrying its own id, and **draining** for a cancelled v1 request until its late frame or its timeout plus 15 s (`:46-53, 1025-1040`); the over-report rule (`:128`, `flag_overreports`).

**Machine settings** (`citar/machine_settings.py`, 3-18): `capabilities.cpu = {enabled, threads, cpu_percent, memory_mb, work}` with `work` a subset of `CPU_WORK = ("lab_game", "ranking_game", "reference_game")` (`:54`), 0 meaning "left to the helper" (`machine_settings.js:108-110`); hardware, models and power modes with the last report kept; `servers.machine_settings(id)` returns slots, swaps and the CPU limits "Phase 4's welcome and settings frames will carry" (`servers.py:773-792`). `servers.trust_tier` and `users.trust_tier` exist, admin-set (`models.py:99, 190-191, 496`); `servers.flags.overreports` is set by the scheduler.

**The ledger** (`citar/ledger.py`, 3-10): `compute_events.verification` is one of `unverified verified pending` (`models.py:720`); model work is `unverified`; `ingest_lab` reads the lab's results files and writes one `cpu` event per game **on the host**, `verified`, whoever played it (`ledger.py:1132-1236`).

**The lab** (`citar/lab.py`): experiments are files (`saves/lab/queue`, `results/NAME.jsonl`, `done/`); `game_spec(exp, i)` is the job unit (`:277-297`); `play()` drives `engine_api.run_game` and builds the result line in Python from the events it hears (`:314-406`); the runner is a separate process (`python -m citar.lab run`) that starts one Python subprocess per game (`:554-670`), adopts orphans through PowerShell and kills them with `taskkill`, Windows only (`:496-538`), honours the host's restricted hours (`:424-430`) and retries a crash three times. Results feed the ratings (`citar/bots/ratings.py`, Bradley-Terry over every result, cached on the files' signature, `:290-335`). The plan's `ranking_game` and `reference_game` have no runner: the dialog names them (`machine_settings.js:17-18`) and nothing else does.

## P4.1 Goals, non-goals and exit

### P4.1.1 What Phase 4 delivers

1. **Protocol v2** (P4.2): one normative specification, typed frames on both sides, and conformance fixtures both sides run.
2. **The Rust helper** (`citar-helper`, P4.3): the same asset names plus Intel Mac, the same configuration files, flags and first-run prompt, a streaming LLM proxy whose cancel really stops generation and which returns raw completions, the hardware scan and power samples, CPU jobs under hard limits where the operating system allows, a machine key, signed results, signed self-update, and service installation per OS.
3. **Jobs in Rust** (`citar-jobs`, P4.4): a closed, typed vocabulary of bot-only work (lab games, ranking games, reference games), a Python-free lab game, the state-hash chain, canonical result hashes, signed claims, and one job host process that runs jobs under limits for both the helper and the server.
4. **The server side** (P4.5): the hub on v2 with tool-call parsing on the server, the job dispatcher with local and remote executors replacing the lab's Windows-only subprocess runner, results into the lab, the ratings and the ledger, trust tiers with replication, sampling, promotion, quarantine and withdrawal, the update relay, and the admin UI.
5. **The Python worker retired**, and a 0.1.5 helper told plainly to upgrade (P4.2.8).
6. **A threat model** (P4.6) written into `SECURITY.md`, and `WORKERS.md` rewritten.

## P4.2 Protocol v2

`crates/citar-helper/PROTOCOL.md` is the normative text (4-01); this section is its summary. The fixtures (P4.2.9) are its executable form.

### P4.2.1 Transport, framing and versioning

- **Transport:** the helper dials out to `wss://<server>/ws/worker` (`ws://` for loopback and plain-HTTP servers), as v1 did, so a v1 helper's attempt still reaches a server that can tell it to upgrade. One WebSocket per machine row; the newest connection wins (`shutdown`, code `replaced`, to the older).
- **One machine is one row** (C4): one helper process, one connection, one token and one key carry both capabilities, LLM and CPU; a machine with no model endpoint runs the helper with `--no-llm` and lends CPU only, and one that lends no CPU says so locally or on the site.
- **Frames:** UTF-8 JSON text frames, each an object with `t` (the type) and `ts` (the sender's Unix time, informational only). At most 8 MB a frame (v1's cap); a `job_result` is well under 1 MB.
- **Versioning:** `hello.protocol = 2`; the server accepts the protocols in `HUB_PROTOCOLS = (2,)`. Inside v2 a change must be additive: a new frame type or a new optional field. Both sides ignore frame types they do not know (logged once per type at debug) and fields they do not know. A breaking change is v3, and whether a release then accepts both is that release's own decision (0.1.6's answer for v1 is no, P4.2.8); a server refuses a protocol it does not speak with P4.2.8's refusal, which every helper from v2 on reads as `refused` code `protocol` and handles by waiting for its own update (P4.3.8). **Job specs are the exception:** they are typed and closed (unknown keys refused), because they decide what code runs and what it computes (P4.4.1).
- **Ids:** request ids (16 hex, the scheduler's), job ids `cj_…` and run ids `cr_…` (the server's), all opaque to the helper.

### P4.2.2 The handshake

**`hello`** (helper → server, first frame, within 30 s of the connection):

| Field | Meaning |
|---|---|
| `protocol` | 2 |
| `token` | the worker token (never logged; v1's redaction) |
| `helper` | `{version, build, jobs_build, target, label}`: the helper's semver version, its engine build id (`citar_bot::build_id`, shown on the card), its jobs compatibility key (P4.4.5), the Rust target triple, `git describe` or `unknown` |
| `machine` | `{hostname, name, os, arch, public_key}`: `name` the owner's `--name`; `public_key` the machine key, base64 of 32 bytes (P4.3.7) |
| `llm` | `{enabled, provider, slots, stream, models: [{key, label, context, loaded}]}`; `enabled` false for a CPU-only helper (`--no-llm`) |
| `cpu` | `{enabled, ceiling: {threads, cpu_percent, memory_mb, work}, limits: {cpu, memory}, verifiable, bots, ruleset}`: the local switch (off unless the machine's owner turned it on, P4.3.2) and the local ceiling (P4.3.6), how hard this OS can hold each limit (`"hard"` or `"soft"` each), the answer of the canary and the self-check (P4.4.3), the bot versions compiled in, the ruleset id |
| `report` | `{hardware, hardware_source}`: the scan (P4.3.5) or the owner's file, as 3-18's report; `hardware_source` is `"scan"`, `"file"` or `"none"` |
| `running` | the run ids the helper is still playing from before a reconnect |
| `results` | the run ids whose results it holds unacknowledged (P4.2.5) |
| `updates` | `auto`, `notify` or `off`: the helper's local policy |
| `quiet_until` | when the helper's own quiet hours in force end, or null |

**The server's answer** is `welcome` or `refused`, then nothing else until the helper has its welcome (3-05's ordering, kept).

`welcome`: `{protocol: 2, machine: {id, name}, settings, ping_s, server: {version, build, jobs_build}, update, jobs: {keep: [...], drop: [...], resend: [...]}}`: `settings` as P4.2.3; `update` the signed manifest the server relays, or null (P4.3.8); `jobs.keep` and `jobs.drop` say which of the helper's `running` runs are still assigned to it (the others it aborts), and `jobs.resend` which of its held `results` the server still wants (the others it deletes).

`refused`: `{code, message, retry_after_s?}`; the server closes the socket after it. The helper's reaction is part of the contract:

| `code` | Why | The helper |
|---|---|---|
| `token` | unknown or revoked token, machine disabled or deleted, owner not active | a **permanent refusal**: says to issue a new token (`citar-helper setup` asks for one); from a console it exits 78; as a service it idles, logs once, and tries again hourly (P4.3.9), so no service manager restarts it into a loop |
| `key` | the machine already has another key registered | a permanent refusal, as `token`, saying the owner must reset the machine's key on the Servers page (P4.5.1) |
| `protocol` | the server does not speak v2: a 0.1.5 server answers a v2 hello with a v1 `error` frame and close code 4426, and a 0.1.6 server answers any hello whose `protocol` is not 2 the same way (P4.2.8); the helper reads either as `protocol` | waits: retries every 10 minutes, logging that the server must be upgraded or its own update applied; never exits on it |
| `rate` | too many refused tokens from this address | retries after `retry_after_s` |
| `build` | reserved for v3 | as `protocol` |

**Server-side checks, in order** (P4.5.1): the protocol (P4.2.8's refusal, which costs nothing and must reach a 0.1.5 helper in the one shape it reads), the address's rate limit (before any lookup), the token, then the key.

### P4.2.3 Settings, catalog, hardware, power and status

- **`settings`** (server → helper, in `welcome` and pushed on every change of the machine's settings): `{llm: {enabled, slots, allow_swaps}, cpu: {enabled, threads, cpu_percent, memory_mb, work, yield_to_llm}}`, from `servers.machine_settings(id)`. `0` for a CPU figure means "the helper's ceiling".
- **`settings_ack`** (helper → server, after each `settings`): `{effective: {llm: {enabled, slots}, cpu: {enabled, threads, cpu_percent, memory_mb, work, yield_to_llm}}, capped: [field, ...], limits: {cpu, memory}}`: what the helper will actually do, each figure `min(site, ceiling)`, `capped` naming where its ceiling won. The scheduler's capacity and the dispatcher's threads read `effective`, never the site's figures alone (C3: local always wins).
- **`catalog`** (helper → server, whenever the endpoint's model list or loaded set changes; the helper polls it every 30 s): `{models: [...]}` as in `hello.llm.models`. 3-18's `record_report` applies it by the models mode, and the scheduler's loaded-model rule follows it at once.
- **`hardware`** (helper → server, when the scan changed, and after a `rescan`): `{scan, source}`. Kept as the last report and applied by the hardware and power modes (3-18, unchanged).
- **`rescan`** (server → helper): scan now (the dialog's "Rescan now", P4.5.11).
- **`power`** (helper → server, once a minute when it can measure anything): `{samples: [{t, gpu_w, cpu_util}]}`, from 10-second readings. Written as the machine's power rows (`usage`'s `power-<machine>-YYYY-MM.jsonl` format, P4.5.7); they are measurements, so the power mode (which governs the static figures) does not gate them.
- **`status`** (helper → server, on change, at most every 5 s): `{quiet_until, llm_in_flight, jobs_running, jobs_paused}`. The scheduler treats a machine whose helper is in its own quiet hours like one in the site's quiet hours (tickets refused as temporary with `retry_at`), instead of learning it from `closed` refusals as v1 forced it to.

### P4.2.4 Completions

- **`request`** (server → helper): `{id, model, messages, tools, params, timeout_s}`. `messages` is the whole OpenAI-format list, system prompt included (and, in `json` tool mode, the JSON protocol appended by the server: the fix of the plan's defect); `tools` OpenAI function definitions, or null; `params` at most `temperature max_tokens top_p seed reasoning_effort` (anything else is dropped by the helper, logged once). The helper decides the endpoint, the key and whether to stream; nothing in a request can change them.
- **`done`** (helper → server): `{id, message: {content, reasoning, tool_calls: [{id, type, function: {name, arguments}}]}, finish_reason, usage: {prompt_tokens, completion_tokens, reasoning_tokens, cached_tokens} | null, gen_s, ttft_s, streamed}`. The completion as the endpoint returned it, assembled from the stream when streaming: **nothing is parsed or repaired on the helper** (P4.5.2). `gen_s` is from sending the HTTP request to its last byte; `ttft_s` to the first token; `usage` null when the endpoint gave none.
- **`error`** (helper → server): `{id, code, message, retryable}` with `code` one of `busy` (at its local slots), `closed` (local quiet hours), `unknown_model` (outside its allowlist), `stopping`, `endpoint` (the local endpoint failed or refused), `timeout`, `bad_request`.
- **`cancel`** (server → helper): `{id}`. The helper drops the HTTP response stream, which closes the connection to the endpoint (LM Studio, Ollama, llama.cpp and vLLM stop a streaming generation when its client goes), and only then answers **`cancelled`** `{id, gen_s, tokens_out}`. A request that finished before the cancel arrived has had its `done`; the cancel is then ignored and nothing more is sent.

The server frees the request's slot when `cancelled` (or a crossing `done` or `error`) arrives. Draining stays only as the safety net for a helper that does not acknowledge within `CANCEL_ACK_SECONDS` (5 s): the slot drains as in P3.3.3 and the machine gets `flags.cancel_unacked` (P4.5.3).

**A lost connection cancels every completion in flight on the helper** (the same drop as `cancel`, with nobody to acknowledge to): the hub has already failed those requests, so a generation nobody will read must not hold the GPU, or the helper's local slots after it reconnects (where the server's next requests would meet `busy`). A transcript holds it: the fake endpoint sees its client gone within 1 s of the socket's close.

### P4.2.5 Jobs

| Frame | Direction | Fields |
|---|---|---|
| `job_offer` | server → helper | `job, run, kind, spec, spec_hash, jobs_build, deadline_s, mem_mb, priority, offer_ttl_s` |
| `job_accept` | helper → server | `run` |
| `job_reject` | helper → server | `run, reason`: `busy`, `build` (not its jobs build), `kind` (not in its local work kinds), `quiet`, `disabled`, `limits` (the job host could not be started under the limits), `memory` (its memory per thread is below `mem_mb`), `bad_spec` (refused by validation, or its hash differs), `unverifiable` (the canary or the self-check failed) |
| `job_progress` | helper → server | `run, round, of, elapsed_s, cpu_s, paused_s, peak_mb`: every 10 s or 25 rounds; it is also the run's heartbeat |
| `job_result` | helper → server | `run, outcome: {result, result_hash, chain: {head, rounds, digests}, cpu_s, wall_s, paused_s, peak_mb}, claim, signature` (P4.4.4) |
| `job_result_ack` | server → helper | `run`: sent once the dispatcher has committed the result (or found it a duplicate) |
| `job_failed` | helper → server | `run, code, message, retryable`: `code` `memory` (the memory limit ended it), `deadline`, `host` (the job host died), `aborted_locally` (the owner stopped CPU sharing), `internal` |
| `job_abort` | server → helper | `run, reason` |
| `job_aborted` | helper → server | `run` |
| `jobs_pause` | server → helper | `reason` (`benchmark`): pause every running game, whatever `yield_to_llm` says |
| `jobs_resume` | server → helper | (none) |

A game that panics is a **result**, not a failure: its outcome is the crash record (P4.4.2), which a replica must reproduce. `job_failed` is for the infrastructure. The same frames, without `claim`, `signature`, the acknowledgement and the offer's time to live, are the job host's own protocol on its standard input and output (P4.4.3), so the helper relays them and signs results, and the server's local executor speaks them directly.

**The rules the frames carry** (each with its transcript, P4.2.9):
- **Results are acknowledged.** The helper writes each result to `helper/results/<run>.json` before sending it and deletes the file only on its `job_result_ack`. After a reconnect it lists the held runs in `hello.results`; the welcome's `jobs.resend` names those the server still wants (sent again at once), and the helper deletes the others. A second `job_result` for a run already settled gets another `job_result_ack` when its hashes are identical, and is a `claim` failure (P4.5.8) when they differ.
- **Offers expire.** A run with neither `job_accept` nor `job_reject` within `offer_ttl_s` (30 s) is `expired` and its job offered elsewhere; a late `job_accept` gets `job_abort`.
- **A silent run expires.** A running run with no `job_progress` for 5 minutes while its helper is connected (the clock restarts at each connection and at the server's start), outside a pause the helper reported, is `expired` and its job re-queued; a late `job_result` for it is acknowledged and dropped (not counted, not credited).
- **Re-offers back off** per (machine, reject reason): 2 s doubling to 10 minutes, cleared for `busy` and `quiet` by a `status` that shows room, and for `build`, `kind`, `disabled`, `limits` and `unverifiable` by the next `settings_ack` or hello.
- **Paused time is reported** (`paused_s`, from `yield_to_llm` and `jobs_pause`) and extends the run's deadline on both sides, up to twice the deadline (P4.5.5).

### P4.2.6 Updates

- **`update`** (server → helper, when the server learns of a manifest while the helper is connected): `{manifest, signature}`, as `welcome.update`.
- **`update_status`** (helper → server): `{state: "available"|"downloading"|"verified"|"restarting"|"applied"|"failed"|"refused"|"unavailable", version, message}`. Shown on the Servers page.

### P4.2.7 Keep-alive and shutdown

- `ping`/`pong` every `ping_s` (20 s); a connection is stale after 70 s without a frame (v1's figures). The helper sends its own ping when it has heard nothing for 45 s, so it notices a dead link without waiting for the server.
- **`shutdown`** (server → helper): `{reason, code}` with `code` `revoked`, `disabled`, `deleted`, `suspended`, `replaced`. The helper aborts its jobs and requests and treats it as a permanent refusal (P4.2.2): from a console it exits 78, as a service it idles and tries again hourly. `replaced` means another process holds the machine's token; an update's hand-off never causes one, because the old process closes its socket before the new one dials (P4.3.8).

### P4.2.8 The v1 transition

**A 0.1.6 server refuses a v1 helper; it does not serve it.** The hub accepts only a hello whose `protocol` is 2. Any other hello (0.1.5's, which carries `version: 1` and no `protocol`; one with another `protocol`; one with neither key) gets one v1-shaped `error` frame (`{"t": "error", "id": "", "message": …}`, the shape the 0.1.5 helper reads) with the message below, and close code 4426: no token lookup, no audit row, no rate-limit count, and at most one log line per address an hour. It is the handshake's first check and a single branch, never a second code path (the owner's decision of 2026-10-14, `ops/p3-notes.md`):

> This server runs CITAR 0.1.6, which needs the new CITAR helper (protocol 2). Download it from the Servers page of this server, or from https://github.com/jprodgers/CITAR/releases/latest, and run it with a token issued there.

The 0.1.5 helper run by hand handles this well: its `Rejected` path logs "The server rejected this worker: <message>" and stops instead of retrying (`agent.py:434-440`). **Run as the system unit `citar setup --worker` installed** (`Restart=always`, `RestartSec=15`, P4.0), it is restarted every 15 s into the same refusal until the unit is disabled: cheap for the server (no lookup, throttled logging) but noisy, so the runbook's first step on such a machine is `sudo systemctl disable --now citar-worker`, and `WORKERS.md` says so. **The other order works too:** a v2 helper whose server is still 0.1.5 receives v1's "This server speaks worker protocol v1..." error and close 4426, reads it as `refused` code `protocol`, and waits, retrying every 10 minutes, so it connects by itself once the server is upgraded. Either side can move first; in between, that machine is simply offline, and nothing half-works.

**Why not accept v1 for a transition window:**
1. **It would buy the owner's machine nothing.** Phase 6 starts the VPS on a fresh database (plan §7), so the Framework Desktop's 0.1.5 token does not exist on the 0.1.6 server; the machine must be registered again and given a new token whatever the protocol, and downloading the new helper is one more step in the same sitting.
2. **It would keep two protocols alive in the hub:** parsing on the helper beside parsing on the server, draining as the normal cancel, `busy` as a routine answer, and a second set of tests, all to serve one machine for a few minutes.
3. **There are no other users** (plan §1, revised), and the plan's own rule is to fix rather than carry.
4. **The owner decided it** (2026-10-14, `ops/p3-notes.md`): protocol v2 only, no compatibility layer, no transition period, no grace mode; the Python worker deleted once the Rust helper replaces it. The development order keeps the same rule: the hub carries exactly one protocol at every merge (P4.11).

**The runbook for Phase 6** (into `docs/server/WORKERS.md` in 4-14): deploy the server; register the machine (or keep its imported row) and issue a token; on the machine, stop the 0.1.5 helper (`sudo systemctl disable --now citar-worker` where `citar setup --worker` installed it as a service; otherwise close it), download `citar-helper-<target>` from the Servers page, run `citar-helper setup` (it reads the old `helper.json`'s endpoint, models and quiet hours, asks for the new token, and asks whether to lend CPU, default no); optionally `citar-helper service install`.

### P4.2.9 Conformance fixtures

- **Where:** `crates/citar-helper/protocol/v2/`: `frames/valid/*.json` and `frames/invalid/*.json` (one frame each, an invalid one with the reason it must be refused), and `transcripts/*.json`.
- **A transcript** is a named sequence of steps: `{"s2h": frame}` (the server sends), `{"h2s": pattern}` (the helper must send a frame matching it next), `{"endpoint": {...}}` (the fake model endpoint's next behaviour: a scripted response, a stream of deltas with delays, or an expectation such as `expect_disconnect_within_ms`), `{"host": {...}}` (the fake or real job host's), and `{"state": {...}}` (an assertion on the receiving side's state, read by that side only: for the hub, "the slot is free and nothing drains"; for the helper, "no request in flight"). Patterns use a small matcher language: `"<any>"`, `"<int>"`, `"<number>"`, `"<string>"`, `"<hex64>"`, `"<base64>"`, `"<id:NAME>"` (binds a value and requires it equal wherever the name recurs), `"<golden:SET/NAME>"` (a value from a committed golden file).
- **Both sides run every transcript.** The Rust side (`crates/citar-helper/tests/conformance.rs`) plays the server's frames and the endpoint from an in-process fake server and checks every frame the real helper code sends. The Python side (`tests/test_helper_conformance.py`) plays the helper's frames from a `FakeHelper` against the real hub (uvicorn, a real WebSocket) and checks the hub's frames and its scheduler's and dispatcher's state. A transcript is therefore checked from both ends; a change to the protocol changes a fixture, and both suites must agree with it.
- **Both sides hold the same frame table:** PROTOCOL.md's table of frame types is parsed by a test on each side and compared with the types each side's code knows.

## P4.3 The `citar-helper` crate

### P4.3.1 Structure and dependencies

- **Crate:** `crates/citar-helper`, a library (`citar_helper`, so tests drive it in-process) and the binary `citar-helper`. Modules: `cli`, `config`, `home` (the directory layout), `log` (redacting), `session` (the WebSocket, handshake, reconnect, dispatch of frames), `protocol` (every frame as a serde type), `llm` (discovery, catalog, the proxy), `scan` (hardware and power), `jobs` (the job host's parent side, signing), `key`, `update`, `service`, `quiet`.
- **The crate graph** (`xtask/src/check/graph.rs`): `citar-jobs: [citar-engine, citar-bot, citar-sim]`; `citar-helper: [citar-engine, citar-bot, citar-sim, citar-jobs]`; `citar-py` gains `citar-jobs`. `citar-store` is not needed by the helper (jobs keep no saves) and stays off its row until something needs it.
- **Dependencies** (workspace entries, each with its reason in the manifest): `tokio` (rt-multi-thread, net, time, process, io-util, sync, signal, fs), `tokio-tungstenite` with rustls, `reqwest` with rustls and streaming, `rustls-platform-verifier` (the OS's own trust store: no CA bundle hunt as in `agent.py:58-87`, no OpenSSL), `serde`, `serde_json`, `clap`, `ed25519-dalek` and `getrandom` (in citar-jobs), `blake3` (workspace), `sysinfo`, `base64`, `semver`, `chrono` (local quiet hours), `thiserror`, `self-replace` (the update's swap on every OS), and per OS `windows-service` and `windows-sys` (Windows), `libc` (Unix). No C toolchain beyond what rustls' crypto backend builds with.
- **`unsafe`:** the workspace keeps `unsafe_code = "deny"`. The only `unsafe` in Phase 4 is in `crates/citar-jobs/src/sys/{windows,unix}.rs`, the OS calls no safe wrapper makes (Job Objects; `setpriority`, `setrlimit`; on Windows the owner-only DACLs of P4.3.7 and P4.3.9), each block with a `// SAFETY:` comment, allowed for that module alone; `cargo xtask check` gains a rule refusing an `unsafe` token anywhere else in `citar-jobs` and anywhere in `citar-helper`, which calls the module's safe functions.
- **Features:** `test-faults` (P4.4.6), `test-update-key` (P4.3.8), `test-jobs` in citar-jobs (the `burn` and `alloc` job kinds the limit tests use) are test features; `dev-guard` is the development build's guard, which `cargo xtask develop` (and so every helper the packages and QA run) always sets: loopback addresses only, and no start without an explicit `--home` outside the platform's per-user base (P4.3.2); `packaged` is Phase 5's, for the tap, bucket and winget builds (P4.3.8). `cargo xtask check` refuses the test features and `dev-guard` in citar-py's dependencies except as a forward of citar-py's own `test-ops`, in `pyproject.toml`'s maturin features, and on any `cargo build` line of `release.yml` and `helper.yml`'s artifact job. **A helper built with a test feature or `dev-guard` dials loopback addresses only** (the server and the update URL; compile-time), so no development or test build can reach a real server; release builds are made only by the workflows.

### P4.3.2 Configuration, compatibility and isolation

- **The home.** `--home DIR` (or `CITAR_DATA_DIR`, as Python) is the per-user base: `helper.json` at its root (v1's place), and the helper's own state under `helper/`: `machine-key.json`, `logs/helper.log` (rotated at 5 MB, three kept), `update/` (staging), `scan.json` (the last scan and its hash), `results/` (unacknowledged results, P4.2.5). Without either, the platform's per-user base (P4.0), which on this laptop also holds the owner's `citar.db`, `secret_key` and `config/`: a `dev-guard` build (P4.3.1) therefore refuses to start without an explicit `--home` outside that base, so a forgotten flag fails instead of writing there. The helper writes nothing outside its home (and the service definitions P4.3.9 writes on request).
- **Compatibility.** Every v1 way of configuring keeps working with the same meaning: `helper.json`, `--config worker.json` (any path), the `CITAR_WORKER_*` variables, every v1 flag, the quiet-hours syntax, the first-run prompt on a TTY (server, token, "remember these in …?"), "Press Enter to close" when a double-clicked binary fails. 4-03's gate 1 holds this against a table recorded from `citar/worker/__main__.py:build_config` before 4-05 deletes it.
- **New settings** (flags and `helper.json` keys): `--no-llm`; `cpu: {enabled, threads, cpu_percent, memory_mb, work}`, the local switch and ceiling. **CPU lending is off by default**, so it is the lender's decision on the machine itself and not only on the site (where an administrator, or a compromised server, could otherwise turn it on): `setup` asks "Lend this machine's spare CPU to the server? [y/N]" and writes `cpu.enabled`; `--cpu` turns it on for one run; turned on without figures, the ceiling is half the logical CPUs, 50% and a quarter of the RAM, every kind. A 0.1.5 `helper.json` has no `cpu` key, so a migrated helper lends no CPU until its owner says so, and the site's dialog then says "not lent by this machine's owner". `updates: auto|notify|off` (default `auto`, `notify` in a `packaged` build, P4.3.8); `stream: true|false` (default true); `--ca-file FILE` (trust a server's own CA, the right answer to a self-signed server); `--no-power`. `--insecure` is kept for compatibility but honoured only for loopback and private (RFC 1918, ULA, `.local`) hosts, with a warning.
- **Subcommands:** `run` (the default; `--service`, which every service definition passes, and on Windows `--detach`, P4.3.9), `setup` (the first-run questions, also to replace a token), `scan [FILE]` (print or write the hardware report: the standalone collector), `service install|uninstall|status|run` (P4.3.9), `update check|apply`, `job-host` (internal: the job host, P4.4.3), `--self-test` (P4.4.3, P4.3.8), `--version` (version, build id, jobs build, target, protocol, and the key's fingerprint when its home holds a key).
- **Isolation in tests** is a rule (P4.7.1): every test and QA run passes `--home` to a fresh directory under its own scratch or QA directory, and sets `CITAR_DATA_DIR` to it as well.

### P4.3.3 The connection

- A single tokio runtime. The session task owns the socket: it reads frames, routes each to its handler (requests to the proxy, jobs to the job side, settings to the limits), and writes through one channel, so a slow handler never blocks pings. Scans, key generation and file reads run on `spawn_blocking`.
- **Reconnect:** 2 s doubling to 60 s with 30% jitter (v1's), reset by a welcome; the `refused` and `shutdown` reactions of P4.2.2 and P4.2.7; a TLS failure is logged with the host and the verifier's reason, never relaxed.
- **On each connect:** discover models (P4.3.4), read or scan hardware (cached; P4.3.5), send `hello` with `running` and `results`, then follow the welcome's `jobs`.
- **On a lost connection:** every completion in flight is cancelled at once (P4.2.4); job runs go on, and their results wait in `helper/results/`.
- **Local policy, enforced here whatever the server asks** (v1's principle, kept): the model allowlist, the local slots, the local quiet hours (no new request or job starts; running jobs finish), the CPU ceiling, the update policy.

### P4.3.4 The LLM proxy

- **Endpoints:** `lmstudio` (`/api/v0/models` for load state and context, else `/v1/models`), `ollama` (`/v1/models`, and `/api/ps` for what is loaded), `openai_compatible`, `openai` (a key from `api_key_env`, read locally, sent only to the configured base URL). The configured base URL and key are the only ones the helper ever dials for completions.
- **Streaming by default:** `stream: true` with `stream_options.include_usage`; the helper assembles content, reasoning (`reasoning_content` or `reasoning`, whichever the endpoint uses), and tool calls from their deltas (by index: id, name, arguments concatenated), and keeps `finish_reason` and the final usage. `stream: false` (or an endpoint that refuses streaming with tools, detected once and remembered for the connection) sends one non-streaming request; its cancel then closes the connection as well, but whether the endpoint stops is its own business (logged). Streaming is chosen for cancel, not for the server: the server still receives one `done` (P4.1.3).
- **Real cancel:** each request is a task holding its response stream; `cancel` aborts the task, which drops the stream and closes the TCP connection (reqwest never reuses a connection whose body was not read to the end); `cancelled` is sent after that, with the tokens received so far. A lost connection to the server aborts every request task the same way.
- **Slots and refusals:** `busy` beyond the local slots, `closed` in local quiet hours, `unknown_model` outside the allowlist, `timeout` when `timeout_s` (capped at 900 s locally) passes, `endpoint` for a connection or HTTP error from the endpoint (with its status and the first 300 characters of its body).
- **Timing:** `gen_s` and `ttft_s` from `Instant`; the server bounds them by what it observed (P3.3.4, unchanged).

### P4.3.5 The hardware scan and power samples

- **`scan`** produces the `citar-hardware` format `hwinfo.collect()` produces (same keys; `collector_version` 2, `collector: "citar-helper"`), so 3-18's `valid_scan`, `clean_hardware`, classes and the dialog read it unchanged: `sysinfo` for the OS, CPU model, cores, threads, RAM, disks and volumes; GPUs from `nvidia-smi --query-gpu` (names, memory, power limit, whether power is readable), on Windows `Get-CimInstance Win32_VideoController` through PowerShell (as `hwinfo.py` does, so the logic and the answers match), on Linux `lspci` and `rocm-smi`, on macOS `system_profiler SPDisplaysDataType SPHardwareDataType -json` and unified memory; the form (a battery means a laptop); runtimes (LM Studio and Ollama answering locally); `power.suggested` from a port of `guess_power`. Every probe is best-effort with a timeout, as in `hwinfo.py`: less information, never an error. **Probes are injectable for tests:** in a `dev-guard` or test build only, `CITAR_HELPER_NVIDIA_SMI`, `CITAR_HELPER_POWERSHELL` and `CITAR_HELPER_SYSTEM_PROFILER` name the probe programs, so a test runs a fake (a small test binary, an `.exe` on Windows). A fake first on `PATH` would not do: on Windows `Command` searches System32 before the parent's `PATH`, and the NVIDIA driver installs the real `nvidia-smi.exe` there (this laptop has one).
- **Auto or manual, per section, is the site's choice** (3-18, unchanged): the helper always reports, the machine's hardware, models and power modes decide what a report may change, and the last report is always kept for "Apply". The helper's own manual is to report a file or nothing.
- **When:** at connect (a cached scan younger than 6 hours is reused), every 6 hours, and on `rescan`; a `hardware` frame only when the scan's hash changed. `--hardware FILE` reports the file instead (read again at each connect, UTF-16 accepted, v1's rule); `--no-hardware` reports nothing.
- **Power:** every 10 s, `nvidia-smi --query-gpu=power.draw` where power is readable and the CPU utilisation from `sysinfo`; one `power` frame a minute. `--no-power` turns it off. Machines without a readable GPU power report CPU utilisation only, and costing keeps using their figures for the rest.

### P4.3.6 CPU jobs on the helper

- **The job host is a child process,** `citar-helper job-host` (P4.4.3), started when CPU work is enabled (site and local switch both), with the effective limits (P4.2.3), and restarted between jobs when the limits change. It reports its `jobs_build` in `ready`, and the parent refuses (and restarts) a host whose build differs from its own, so a host left from before a binary swap never computes with the old code (P4.3.8). Its standard input and output carry the job frames; the helper relays them to and from the server, checks them, and signs results (P4.3.7). Running the games in a child keeps a crash, an out-of-memory kill or a hung game away from the connection, and gives every OS one process to put its limits on.
- **How each OS holds the limits** (C3: "hard where the OS allows"):

| OS | CPU (`cpu_percent` of the whole machine) | Memory (`memory_mb`, all jobs together) | Reported |
|---|---|---|---|
| Windows | the job host puts itself in a Job Object with `JOB_OBJECT_CPU_RATE_CONTROL_ENABLE` and `HARD_CAP`, `CpuRate = percent x 100`, at `BELOW_NORMAL_PRIORITY_CLASS` | the same Job Object's `JobMemoryLimit`, with `KILL_ON_JOB_CLOSE` | hard, hard |
| Linux with a reachable user manager | the parent starts it under `systemd-run --user --scope --quiet --collect -p CPUQuota=<percent x CPUs>% -p MemoryMax=<MB>M -p TasksMax=<threads + 16>`; the job host reads its own cgroup's `cpu.max` and `memory.max` to confirm | as left | hard, hard |
| Linux otherwise | `nice 10` and the thread cap only | `RLIMIT_DATA` (private writable memory: `RLIMIT_AS` would count the address space glibc reserves per thread) | soft, hard |
| macOS | background priority (`PRIO_DARWIN_BG`, efficiency cores on Apple silicon) and the thread cap | a watchdog in the job host reads its resident size every 500 ms and ends the jobs past the limit | soft, soft |

- **`threads`** is the most games at once (one thread each); the server never offers more, and the host refuses more (`busy`).
- **`yield_to_llm`** (a site setting, default on): while any model request of this helper is in flight, the job host is told `pause` and stops every game at its next seat step (each well under a second), then `resume`. A GPU machine lending its spare CPU does not slow its own model. **Benchmarks:** while a benchmark lease is live on the machine, the server offers it no CPU job and sends `jobs_pause` (whatever `yield_to_llm` says), then `jobs_resume` when the lease ends (P4.5.5), so running games never contaminate a benchmark's timing.
- **Deadlines:** the helper aborts a run past its `deadline_s` itself (`job_failed` `deadline`), not counting paused time, up to twice the deadline in all; it reports `paused_s`, and the server's own timeout, extended the same way, is only the backstop.
- **Reconnects:** a run continues across a lost connection; the next `hello` lists it in `running`, and the welcome says whether to keep it. A result is written to `helper/results/` before it is sent and kept there until its `job_result_ack`, so one produced while disconnected, or sent just before a connection died, is sent again after the reconnect if the welcome's `jobs.resend` asks for it (P4.2.5).

### P4.3.7 Keys and signing

- **The machine key** is an ed25519 key generated on first run from the OS's random source (`getrandom`), stored in `helper/machine-key.json` (`{"v": 1, "public": base64, "secret": base64}`), written with mode 0600 on Unix and, on Windows, with an owner-only DACL (its owner, SYSTEM and Administrators; protected from inheritance; set through citar-jobs' `sys` module, P4.3.1). **At start the helper refuses a key file anyone else can read:** group or others on Unix, as SSH does; any other principal in its DACL on Windows, where a `--home` such as `C:\citar` inherits Authenticated Users' modify rights and anything under `%ProgramData%` inherits Users' read. A `helper.json` (it holds the token) that others can read gets a warning and the command that fixes it. The secret never leaves the machine: it is not in any frame, log or scan.
- **Registration:** the first v2 hello of a machine registers its public key on the row (trust on first use, bound to a valid token); a later hello with another key is refused (`key`) until the owner or an admin resets the machine's key (audited, P4.5.1). A token issued again keeps the key. A key reset never changes the machine's trust (P4.5.8): a quarantined machine stays quarantined with a new key. The Servers page shows the key's fingerprint (the first 16 hex of blake3 of the public key), which `citar-helper --version` also prints, so an owner can check it is their machine.
- **Signing:** the helper signs each claim the job host's outcome yields (P4.4.4) before relaying the result. Signing in the parent keeps the key away from the job host, which runs the games.

### P4.3.8 Self-update

- **The manifest** (`citar-helper-manifest.json`): `{v: 1, version, protocol, build, released_at, assets: {<target>: {name, url, sha256, size}}}`, the five targets of P4.10. It is signed as a whole: `citar-helper-manifest.json.sig` = ed25519 over `"CITAR-HELPER-MANIFEST-V1\0" ‖ the manifest's bytes as published`. Both files are release assets beside the binaries.
- **Trusted keys:** the helper embeds the public keys in `crates/citar-jobs/update-keys.pub` (one base64 key per line, up to two, for rotation). **In Phase 4 that file is empty:** no real key exists yet, and a build that trusts no key reports updates `unavailable` and never downloads anything. Phase 5 adds the owner's public key (the owner question on custody, P4.10). Only a build with `test-update-key` also trusts a key given at run time (`--update-key FILE`), and only such a build reads `CITAR_HELPER_VERSION` at compile time to call itself another version.
- **Where the manifest comes from:** the server relays it (`welcome.update` and `update`); the helper does not poll GitHub. The server fetches the manifest **of its own version** (`helper_manifest_url`, default `https://github.com/jprodgers/CITAR/releases/download/v{version}/citar-helper-manifest.json` and its `.sig`; or `helper_manifest_file` for tests), at most hourly, off any request path, and relays it only if it verifies against the same keys (P4.5.9). Helpers therefore follow the server they serve: same engine build, same protocol.
- **The helper's steps,** under its local policy (`off`: ignore; `notify`: report `available` and stop there; `auto`):
  1. verify the signature against the trusted keys; refuse otherwise (`update_status refused`);
  2. refuse unless `version` is newer than its own (no downgrade, so a server cannot push an old signed build with a known flaw), and unless the manifest has its target;
  3. refuse a URL that is not `https`, or `http` to a loopback host (tests);
  4. download into `helper/update/` and check `size` and `sha256`, following redirects only to `https` URLs (at most five: GitHub serves release assets from another host); the integrity is the signed hash and size, never the host;
  5. run the staged binary with `--self-test` (it starts as far as loading its embedded ruleset, running the job canary and the self-check of P4.4.3, then prints its version, build, jobs build and target, which must equal the manifest's): the guard against a binary that cannot run, or computes differently, on this machine;
  6. wait until idle (no request or job in flight; at most an hour, then between two jobs);
  7. **the hand-off:** the old process stops taking work, stops its job host, sends `update_status restarting`, closes its socket, writes `helper/update/pending` (the old and new versions, a start count), and swaps the binary with `self-replace`, keeping the old one as `<name>.old`. Then:
     - **a console run** starts the new binary as its child and becomes its **supervisor**: it waits on the child and exits with the child's code. If the child exits before `helper/update/healthy` exists, the supervisor restores `.old`, runs it in the child's place, and that process reports `failed`.
     - **a service run** (`--service`, or under `run --detach`'s supervisor) exits with code 75, and its supervisor or service manager starts the new binary (P4.3.9). Rollback is the new binary's own start path: it reads `pending` first thing, counts the start, and on the third start without `healthy` restores `.old` and exits 75, so the manager starts the old binary, which reports `failed`.
     - The new binary writes `helper/update/healthy` after its first welcome, or after 60 s of running while the server cannot be reached, deletes `pending`, and reports `applied`. `replaced` is never the success signal: the old process closed its socket before the new one dialled. `citar-helper update rollback` restores `.old` by hand.
- **The job host follows the binary:** it is stopped at step 7, and a host whose `jobs_build` differs from its parent's is refused (P4.3.6).
- **Packaged builds** (Phase 5's Homebrew tap, Scoop bucket and winget package) are built with the `packaged` feature: `updates` defaults to `notify`, and `auto` is refused with "update through your package manager", so the helper never fights the package manager over its own binary. The GitHub release assets are built without it.
- **Who signs** is Phase 5's (P4.10): `cargo xtask keygen --out DIR` (refuses a directory inside the repository), `cargo xtask helper-manifest --assets DIR --version V` and `cargo xtask sign-manifest --key FILE MANIFEST` (refuses a key file inside the repository or known to git) exist from 4-13, so whichever custody the owner chooses has its tools. (xtask signs with `ed25519-dalek` directly; its row of the crate graph stays empty, and the bytes it signs are the manifest file as published, so no shared type is needed.)

### P4.3.9 Service installation

`citar-helper service install|uninstall|status|run [--user|--system] [--dry-run]`. Every definition runs the helper with `--service`, an explicit `--home` and the absolute path of the binary; `--dry-run` prints what would be written and run, and changes nothing.

**Exit codes are part of the contract:** 0, stopped by the user or the service manager; 75, restart for an update (P4.3.8); 78, a permanent refusal (P4.2.2, P4.2.7), from a console run only; anything else, a crash. **In service mode a permanent refusal does not exit:** the helper idles, logs once, and tries again hourly, because launchd cannot exclude an exit code from `KeepAlive` and a helper restarted every 15 s would retry a revoked token forever (and, before P4.5.1's fix, lock its neighbours out of the rate limit).

| OS | `--user` (default where possible) | `--system` |
|---|---|---|
| Linux | `~/.config/systemd/user/citar-helper.service` (`Restart=on-failure`, `RestartSec=15`, `RestartPreventExitStatus=78`, `NoNewPrivileges=yes`), then `systemctl --user daemon-reload` and `enable --now`; it prints the `loginctl enable-linger` line for running without a login, and never runs it | `/etc/systemd/system/citar-helper.service` with a `User=` and the same restart rules; needs root, and says how rather than elevating |
| macOS | `~/Library/LaunchAgents/org.citar.helper.plist` (`RunAtLoad`, `KeepAlive` with `SuccessfulExit` false, `ThrottleInterval` 15, logs into the home), `launchctl bootstrap gui/<uid>` | not offered |
| Windows | a value `CITAR helper` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` running `citar-helper run --detach --home …`: `--detach` starts, with no window, a small **supervisor** that runs the helper as its child in service mode and starts it again at once after exit 75 and after a crash with backoff (15 s doubling to 10 minutes), and stops on 0; logs to the file | a Windows service (`windows-service`; `service run` is its entry), started automatically, running as the virtual account `NT SERVICE\citar-helper` (not LocalSystem: network-facing code that parses server data needs no more); `install --system` copies the binary into `%ProgramData%\CITAR\helper\bin` (so self-update can write it), sets the home `%ProgramData%\CITAR\helper` to a DACL of SYSTEM, Administrators and that account only with inheritance from `%ProgramData%` off (which would give Users read of `helper.json` and `machine-key.json`), and sets failure actions (restart after 15 s, with `fFailureActionsOnNonCrashFailures` so a non-zero exit such as 75 counts); installing needs an elevated prompt, and an unelevated `install --system` prints the elevated command and exits 2 |

A service's restart after exit 75 is the update's restart (P4.3.8). On this laptop only `--dry-run` runs on Windows, in a test that first checks the process is not elevated and aborts if it is; real installs run in WSL with `systemd --user` (P4.7.1); the Windows service and launchd install for real in CI only (P4.7.10).

### P4.3.10 What the helper never does

It never runs a command, a script or code it was sent; never reads or writes a file outside its home (and the service files it was asked to write); never dials anything but its server, its configured model endpoint and, for an update, the signed manifest's asset URL and the `https` redirects it leads to (the file is trusted by its signed hash, not by its host); never loads, unloads or swaps a model; never changes a system setting. It runs only the engine and bots compiled into it, on specs that are data (P4.4.1). These are the claims `WORKERS.md` makes to a lender and `SECURITY.md` defends (P4.6).

## P4.4 Jobs and proof of work (`citar-jobs`)

A library crate shared by the helper and the server's bindings: the job vocabulary, the Rust lab game, the job host and its limits, hashes, claims and signatures, and the update manifest's verification. Everything that must give the same bytes on both sides of the wire lives here, once.

### P4.4.1 Job kinds and specs

| Kind | What it is | Spec | Result |
|---|---|---|---|
| `lab_game` | one game of a member's (or an admin's) lab experiment | `LabSpec`: `lab.game_spec(exp, i)`'s keys, typed (`exp, i, seed, map_type, size, speed, turns, difficulty, barbarians, barbarian_difficulty, nation, city_states, ai_base_values, map_edges, river_density, resources, seats[{label, bot, difficulty, params, aggression, profile, profile_rev, profile_name, levels, nation}]`) | `LabResult`: today's result line, P4.4.2 |
| `ranking_game` | a game of a ranking experiment: the site's own ladder (an experiment with `kind: "ranking"`, admins only, always `collection`) | `LabSpec` | `LabResult` |
| `reference_game` | a game of a reference run: the statistical baseline the bots are compared against (an experiment with `kind: "reference"`, admins only, `collection`) | `ReferenceSpec {i, seed, size, map_type, barbarians, speed, turn_limit, params}`: one game of citar-sim's baseline, typed, with no budget, path, workers, name, smoke or checks (the baseline's `Options` describes a run of many games on one machine, P4.0) | `ReferenceResult`: the baseline writer's game line (`summarize.py` reads it) without `seconds` and `cpu_s`; a crash as `{crash: message}` only |

- **No wall-clock budget:** a job never runs with `RunSpec.budget`. Its deadline (P4.3.6, P4.5.5) ends a run as `job_failed deadline`, never as a result, and `SimError::TimedOut` is never an outcome, so a slow, capped or paused machine computes the same result as a fast one.
- **Closed and typed:** specs deserialize with `deny_unknown_fields`; bounds are checked (players within the ruleset's limits, a known size, map type, speed and difficulty, `turns` at most the speed's time-victory turn, bot versions compiled in, overrides through `citar_bot`'s own `clean`, strings at most 200 characters, `i` below 1,000,000). A spec is data: no path, URL, code or ruleset text. The kinds differ only in who may queue them and which machines opt in (`capabilities.cpu.work`), so an owner may lend CPU to the site's ladder without lending it to members' experiments.
- **`spec_hash = blake3("CITAR-SPEC-V1\0" ‖ kind ‖ "\0" ‖ canonical bytes)`**, where the canonical bytes are the typed spec re-serialized by serde (fixed field order, maps as `BTreeMap`). The server computes it when it creates a job (through the binding); the helper and the job host recompute it and reject a mismatch (`bad_spec`).

### P4.4.2 The lab result in Rust

- `citar_jobs::lab::play(spec, control) -> LabOutcome` ports `lab.play()`'s result building (`lab.py:314-406`): the players by `str(pid)` with label, bot, difficulty, alive, levels, profile and revision, build, version, fingerprint, clean params, fixed and played aggression, score and share, rank, techs, cities, policies, religion, great people, spaceship parts, unhappy share, checkpoints at 50…300 with the twelve stat keys, era turns, the event counts and the 25 most built items; the winner, its label, the victory and the turns. Integer maps are `BTreeMap`, so the JSON is the same bytes on every target.
- **The deterministic part** is everything above plus `exp`, `i`, `seed`, `map`, `engine` (the jobs build, P4.4.5) and `errors`, which holds the bots' error messages only, normalised (no traces, no addresses; `Crash::record()` puts traces there today, P4.0). `seconds`, `started_ts`, `cpu_s`, `finished` and any trace are measurements or diagnostics, outside the hash, added by whoever writes the line.
- **Crashes:** a panic caught by the runner is the outcome `{crash: {turn, player, label, message}}` (the message only; the backtrace is logged, not hashed: frame addresses differ between builds of one source). It is final: recorded in `crashes.log`, never retried (a Rust panic is a bug, not bad luck; 0.1.5's three retries were for a Python process dying), and a replica must reproduce it.
- `lab.play()` in Python becomes a call of `engine_api.run_job("lab_game", spec)` (4-07); the Python result building and its event listener go.

### P4.4.3 The job host and its limits

- **One program, two parents:** `citar_jobs::host::main(stdin, stdout)` is the job host; the helper runs it as `citar-helper job-host`, the server as `python -m citar.jobs host` (which calls it through the extension). Its protocol is the job frames of P4.2.5 as JSON lines, plus `pause`, `resume` and `limits` (sent once at start, with the parent's `jobs_build`) from the parent, and `ready {limits: {cpu, memory}, verifiable, jobs_build}` and `heartbeat` to it. A host whose `jobs_build` differs from the one in `limits` refuses to start, and a parent refuses a `ready` with another one (P4.3.6).
- **Inside:** at most `threads` runs, each on its own thread with its own `Runner`; between seat steps each run checks its abort flag, the pause flag and its deadline (paused time not counted), so abort and pause take effect within one seat step; progress every 10 s or 25 rounds.
- **Verifiable or not, at start:** the canary checks that denormals are neither flushed to zero (`black_box(f64::MIN_POSITIVE) / 2.0 != 0.0`) nor read as zero (`black_box(f64::MIN_POSITIVE / 4.0) * 4.0 == f64::MIN_POSITIVE`), and the **self-check** plays the shortest job of the `jobs` golden set (embedded, P4.4.5) and compares its result hash and chain head with the committed ones. Any failure makes `verifiable: false`, which refuses every job (`unverifiable`) rather than producing results nobody could check: a target or environment that computes differently is never offered work, so it is never quarantined for it. `citar-helper --self-test` runs the same checks.
- **Memory is counted:** the job host's `#[global_allocator]` is a counting wrapper of the system allocator with per-run-thread live and peak tallies (a thread-local run id), so `job_progress` and `job_result` carry each run's real peak, and the server's cost table learns from them (P4.5.4).
- **Limits** (`citar_jobs::limits::apply`) are applied by the host to itself at start, per the table of P4.3.6 (Windows: a Job Object it creates and joins, legal since Windows 8's nested jobs; Linux: confirms the scope its parent made, else `RLIMIT_DATA` and `nice`; macOS: background priority and the watchdog). The parent side (`citar_jobs::host::spawn` for the helper, `citar/jobs/host.py` for the server) adds the `systemd-run --user --scope` wrapper on Linux when `systemctl --user` answers, and reads `ready` to learn what holds.
- **Ending:** standard input closing (the parent died) aborts every run and exits within 2 s, so no game outlives its parent: this replaces 0.1.5's orphan adoption. **A memory death ends the whole host**, and the parent classifies it from what it sees: the `memory allocation of N bytes failed` line on the host's standard error (Rust's abort when a Job Object's memory limit or `RLIMIT_DATA` refuses a commit), a SIGKILL with the cgroup's `memory.events` `oom_kill` raised, or the abort's exit code. Every run of that host then fails as `memory`; the dispatcher raises each job's `mem_mb` estimate to the largest peak its run reached and offers it only to executors with room (P4.5.5). Any other death fails the runs as `host`, which are retried.

### P4.4.4 Hashes, the chain, the claim, the signature

- **`result_hash = blake3("CITAR-RESULT-V1\0" ‖ kind ‖ "\0" ‖ serde_json bytes of the typed deterministic result)`.** The server never hashes Python JSON: it passes the received result through the binding, which parses it into the typed result (refusing unknown keys), re-serializes it and hashes, and compares with the claim.
- **The chain** (the plan's "per-turn state-hash chain": one digest per round, after every seat's turn of it): every job game runs with `set_chain(DigestChain::new(spec_hash))`; the outcome carries the chain's head, its round count and every round's digest (64 hex each: about 21 KB for a 330-round game). The server checks that the digests fold to the head from `chain_0` (`chain_check` in the binding); replicas compare heads, and on a mismatch the first differing digest names the round where two machines parted.
- **The claim** (typed, fixed field order): `{v: 1, job, run, machine, kind, spec_hash, jobs_build, bots, result_hash, chain_head, rounds, key}`, `bots` the sorted bot versions the spec names, `machine` the id the welcome gave, `key` the public key. **`signature = ed25519(secret, "CITAR-CLAIM-V1\0" ‖ the claim's bytes)`.** The run and machine ids inside it make a signature useless for any other run; the spec hash and jobs build bind it to exactly what was asked for.
- **Server-side verification** (`engine_api.verify_claim(claim, signature, public_key, result, chain)`): the signature against the registered key, the claim's job, run, machine, kind, spec hash and jobs build against the server's records, the result's hash, the chain's fold. Any failure rejects the run and quarantines its machine as a tampering verdict (P4.5.8): a correct helper never produces one.
- The server's own executor's results are not signed: it is the server (P4.5.6).

### P4.4.5 Determinism the proof stands on

- Every job's game is the engine's ordinary game under `set_chain`; the engine's determinism rules (the keyed RNG, `libm`, defined iteration orders, the lint against hash iteration) and the five-target matrix already hold it.
- **The jobs build,** the compatibility key every job carries: `jobs_build = hex12(blake3("CITAR-JOBS-BUILD" ‖ build_id ‖ SIM_CODE ‖ JOBS_CODE ‖ flavour))`. `SIM_CODE` and `JOBS_CODE` are the content codes of citar-sim and citar-jobs, made by the same `content_code.rs` machinery as the engine's and the bot's (both crates gain build scripts in 4-07), so a change to the runner or to how a result is built changes it. `flavour` records `debug_assertions`, `overflow_checks` and the engine's `checks` feature: a `ci` build and a `release` build can compute different outcomes (a `debug_assert!` that fires is a crash in one and nothing in the other). `hello.helper.jobs_build`, `job_offer.jobs_build`, the claim, `cpu_jobs.jobs_build` and the local executor's report carry it; the build id alone stays what the card shows.
- **A `jobs` golden set** (4-07; `crates/citar-jobs/golden/jobs.json`, checked by citar-jobs' own test binary, which builds the engine without `legacy` or `test-ops`, unlike citar-testkit): four short jobs (two lab duels of 30 rounds, a small four-bot lab game capped at 40 rounds, one reference game capped at 40), each with its spec hash, chain head, rounds and result hash; blessed by the same rule as `cargo golden` (a bless commit saying why). It runs in both the `ci` and the `release` profiles: locally on Windows (S7) and in WSL (S9), and in `determinism.yml` and `helper.yml` on the five targets (CI-only). The helper and the job host embed its shortest job as their self-check (P4.4.3). A target that computes another result fails there before any volunteer's machine does, and a machine whose own build does fails its self-check and is offered nothing.
- **Results are only compared within one jobs build:** a job offered to a helper of another jobs build is rejected (`build`), and the dispatcher never matches or compares across jobs builds. QA builds the helper and the extension in the same profile (`cargo xtask develop`'s, `ci` unless `--release`) and records which. A mismatch within one jobs build that the self-check did not catch is reported as "tampering or an incompatible build" (P4.5.8), never as tampering alone.

### P4.4.6 Faults for testing

`citar-helper --features test-faults` adds `--test-fault MODE`: `result:N` (from the Nth job, alter one score in the result and recompute its hash, so the claim is validly signed and the content wrong: the cheater), `result-at:N,M,…` (alter only the listed jobs, counted from the machine's first: the selective cheater), `digest:R` (alter round R's digest and fold the chain from it: broken hardware), `sig` (sign with another key), `cpu:F` (report F times the CPU seconds), `abandon:N` (accept the Nth job and never finish it), `hold:S` (hold each result S seconds before sending it, reporting the held time as CPU). Each mode's detection is a gate of 4-11 or 4-12 and the exit.

## P4.5 The server side

### P4.5.1 The hub on v2

- **`/ws/worker`** keeps its path (where v1 helpers dial, so they can be told to upgrade). Its order: (1) the protocol: anything but `protocol == 2` gets P4.2.8's message and 4426 (no lookup, no count, throttled logging); (2) the address (`ratelimit.client_ip`, honouring the trusted hops: defect P4.0 (2)) is checked against `worker_auth` **before** any lookup, and an address over it is `refused rate` with `retry_after_s`; the limit counts **distinct** failing token hashes per address (kept in memory for the window), so a helper retrying one revoked token counts once and cannot lock its owner's other machines behind the same address out, while a brute force, whose tokens all differ, is counted in full; (3) the token: a failure counts toward the limit and is audited (as today); (4) the key (P4.3.7); (5) registration (`admit`, 3-05's double check, unchanged), `welcome`, then `record_connection` off the loop. `WorkerToken.last_ip` and `last_seen_at` are written on success.
- **Frames from the helper** are handled on the event loop without blocking it: completions resolve their pending requests (as today); `cancelled` frees the slot (P4.5.3); `catalog`, `hardware` and `power` go to `asyncio.to_thread` writers (`record_report`, the power rows); `settings_ack` and `status` update the connection and call `scheduler.helper_changed`; job frames are put on the dispatcher's queue (P4.5.5), never handled on the loop.
- **Settings are pushed:** the settings route (`PUT /api/machines/{id}/settings`) already refreshes the scheduler; it now also calls `hub.push_settings(id)`.
- **The machine row gains** `public_key`, `key_at`, `helper` (the last hello's helper block, limits and update state) and `trust` (P4.5.8), in revision `0016c_helper_jobs` (P4.5.4).
- `WorkerConnection` keeps one protocol. The hub is v1 until 4-05 and v2 only from 4-05, the package that also deletes the Python worker (P4.11); v1's frame definitions (`citar/worker/protocol.py`) go with it, replaced by `citar/server/helper_protocol.py` (4-01).

### P4.5.2 Tool-call parsing on the server

- `citar/agents/providers/completion.py` (new) holds `parse_completion(message, finish_reason, mode, tools) -> (StepResult, assistant_entry)`: the post-processing `OpenAIConversation.step` does today (native calls, `__invalid_json__`, `repair_tool_calls`, text calls in XML, GLM, plain and Gemma 4 syntax, the JSON protocol), moved without change of behaviour.

One parser, so a model's quirk fixed once is fixed for helpers too: the 3-19 Gemma 4 fix needed shipping to helpers; from 4-05 it never will.
- Usage maps `prompt_tokens`, `completion_tokens`, `completion_tokens_details.reasoning_tokens` and `prompt_tokens_details.cached_tokens` onto the server's usage keys; tokens are capped as P3.3.4 says.

### P4.5.3 The scheduler on v2

- **Capacity** = the site's slots capped by the helper's `settings_ack.effective.llm.slots` (it was `hello.max_concurrent`).
- **Cancel** (`WorkerConversation.close` → `hub.cancel`): the caller's wait ends at once, as today; the slot is freed by `cancelled` (or a crossing `done`/`error`). If neither comes within `CANCEL_ACK_SECONDS` (5 s), the slot drains as P3.3.3 describes and the machine's `flags.cancel_unacked` counts it (shown to admins). A v2 helper that drains is misbehaving; draining is no longer the normal path, which is what 3-19's "Left for later" asked.
- `busy` from a v2 helper means its local slots are below the site's and its `settings_ack` was missed: the existing lower-and-requeue rule (P3.3.3) stays as the net.
- A helper's `status.quiet_until` is read like the site's quiet hours.

### P4.5.4 The job store (revision `0016c_helper_jobs`)

One Alembic revision (4-02, "schema first" as in P3.10.1) with every Phase 4 table and column; later packages fill in behaviour.

- **`cpu_jobs`:** `id` (`cj_…`), `kind`, `ref` (`lab:<exp>:<i>`, the ledger's activity id of 3-10), `item_kind`/`item_ref` (the owned experiment, for access), `owner_id` (the consumer; null for `collection`), `spec` (JSON), `spec_hash`, `jobs_build`, `priority`, `mem_mb` (the memory estimate, raised by a memory death), `state` (`queued running settling accepted crashed failed withdrawn cancelled`), `accepted_run`, `result_hash`, `attempts`, `created_at`, `updated_at`; indexed on (`state`, `priority`, `created_at`) and on `ref`.
- **`cpu_job_runs`:** `id` (`cr_…`), `job_id`, `machine_id`, `executor` (`local`/`remote`), `role` (`primary`, `replica`, `tiebreak`), `state` (`offered running done failed aborted expired`), `offered_at`, `started_at`, `last_progress_at`, `ended_at`, `deadline_at`, `cpu_s`, `wall_s`, `paused_s`, `peak_mb`, `result` (JSON, pruned once the job is settled), `result_hash`, `chain_head`, `rounds`, `digests` (JSON, pruned once matched; kept as evidence on a mismatch), `claim`, `signature`, `acked_at`, `verdict` (`reference match mismatch unchecked rejected`), `error`.
- **`job_costs`:** per (`kind`, `size`, `seats`, `rounds` bucket of 50): `cpu_s` (the median over the local executor's and verifiers' runs: the **reference cost**), `peak_mb` (the 95th percentile of every run's counted peak), `samples`, `updated_at`; seeded from a committed table measured on the golden and benchmark jobs (4-09), so the first jobs already have an estimate.
- **`servers`:** `public_key`, `key_at`, `helper` (JSON), `trust` (JSON: `{verified, streak, mismatches, last_verified_at, last_mismatch, abandons, since, verifier, speed}`: `since` the registration or the last release from quarantine, `verifier` an administrator's mark, `speed` the machine's measured speed against the reference cost).
- **`compute_events.verification`** gains `rejected` (a string column: no DDL); `settings_kv.verification` holds P4.5.8's settings.

### P4.5.5 The dispatcher

- **`citar/jobs/dispatcher.py`:** one thread per server process (like the scheduler and the ledger writer), restarted if it dies, surviving an exception in its loop; it wakes every 2 s and on events (a job frame, an executor change, a new experiment). Its state is the database; its in-memory view is rebuilt at start, which re-queues every run that was `offered` or `running` on the local executor (whose job host died with the old process) and keeps remote runs until their helpers reconnect or their deadlines pass.
- **Jobs come from the lab's queue:** experiments by priority then age (`lab.load_queue`, unchanged files), each game without an accepted result and without a live job becomes a `cpu_jobs` row, at most 4 x the executors' total threads queued ahead (so a 10,000-game experiment does not become 10,000 rows at once). An experiment whose games are all accepted moves to `done/` (as today).
- **Matching** a queued job to an executor with a free thread, highest priority first, round-robin across owners within a priority. An executor is eligible when: online; CPU enabled on the site and by the machine's own switch, with the job's kind in its effective `work`; the same jobs build; `cpu.verifiable`; its effective memory per thread (`memory_mb / threads`) covers the job's `mem_mb`; not quarantined, nor its owner (`users.trust_tier = quarantined`); within P4.5.8 rule 3's caps on `new` machines; outside the site's restricted hours and its helper's own quiet hours; no benchmark lease live on it (P3.3.6's rule extended to CPU); not backing off this job's reject reason (P4.2.5); and the job's owner may use it: their own machine; a `collection` job on a machine whose owner opted into that kind; or a grant on its group whose purposes **list `lab` explicitly**, checked by `admission.check(..., purpose="lab")` (3-09's admission, its budget included). **CPU work is opt-in per grant:** `_purpose_ok` changes so an empty purposes list means every model purpose and never `lab`, and a grant made to lend a GPU for games never lends the CPU. **Administrators' bypass of grants does not apply to CPU work:** an administrator's own lab experiment is eligible where a member's would be, and only the `collection` kinds go to every machine that opted into them.
- **Deadlines:** `deadline_s = clamp(10 × expected, 300 s, 6 h)`, where `expected` is the cost table's `cpu_s` for the job (P4.5.4) divided by the executor's effective share of a core per game (`cpu_percent / 100 × logical CPUs / threads`, at most 1) and by its measured speed (`trust.speed`, 1 until known). Paused time (`paused_s`) extends a run's deadline, up to twice it. A run past its deadline plus 60 s, an offer unanswered after `offer_ttl_s`, and a running run with no progress for 5 minutes while its helper is connected, outside a reported pause, are `expired` and their jobs re-queued (P4.2.5). A machine with three expired or abandoned runs in an hour gets no offer for an hour (`trust.abandons`); an expiry caused by a pause never counts.
- **Failures:** `job_failed` with `retryable` re-queues the job (at most 3 attempts, then `failed`, shown on the Lab page); `memory` raises the job's `mem_mb` to the peak its run reached before re-queueing it (P4.4.3); a crash outcome is accepted as the game's outcome (P4.4.2) once verified like any result.
- **Pause:** `citar lab stop` and the Lab page's Stop pause the dispatcher's offers (running runs finish); `citar lab resume` resumes. **A benchmark lease** going live on a machine sends it `jobs_pause` (the local executor's host gets `pause`), whatever `yield_to_llm` says, and its end `jobs_resume`.

### P4.5.6 Executors

- **The local executor** (`citar/jobs/local.py`) is the host's machine row: it runs a job host child (`python -m citar.jobs host`) with the host row's CPU settings, restarted if it dies, ended with the server. It is **trusted by definition** (it is the server): its runs' verdict is `reference`, and it is the verifier every `new` machine's replicas run on (P4.5.8). Its report carries the extension's `jobs_build`, so a server built in another flavour than a helper never meets that helper's jobs (P4.4.5). Defaults for the host row: local mode, CPU on with threads = half the logical CPUs; server mode, on with 1 thread, 50% and min(1,024 MB, 25% of the RAM) (the VPS has one vCPU and 961 MB, plan §9, so about 240 MB there, below what the OOM killer would take from the server itself; jobs whose `mem_mb` does not fit go elsewhere; an admin raises or lowers them in the host's machine settings). These replace the lab runner's `workers`/`night_workers` (`saves/lab/config.json`); the host's restricted hours replace `quiet_now`. On the VPS, a system service with no user manager, the local job host's CPU share is soft (`nice` and its one thread are the real cap) and its memory hard (`RLIMIT_DATA`); the host's card says so like any machine's.
- **Remote executors** are connected helpers: the dispatcher sends `job_offer` through the hub (`send_threadsafe`), and job frames come back through its queue. Threads are the helper's `settings_ack.effective.cpu.threads`.
- **Replacing the lab runner:** `lab.run`, `_runner_step`, `_Adopted`, `_find_running_games`, `_collect_orphans`, `cmd_play`, the job files and the status file go (4-09); `python -m citar.lab run` and `citar lab run` say the lab now runs inside the CITAR server (local or server mode) and exit 2; `submit`, `status`, `report`, `stop` and `resume` stay. `lab.overview()` reads the dispatcher.

### P4.5.7 Results into the lab, the ratings and the ledger

- **The lab:** an accepted job appends one line to `saves/lab/results/<exp>.jsonl` (`reference` experiments to `saves/lab/reference/<name>.jsonl`), as `_record` does today, plus `executor: {machine, run, verification}`. Writes go through `fsutil` (replace on rewrite) on the dispatcher's thread. A **withdrawal** rewrites the file without the withdrawn lines (P4.5.8).
- **The order of writing** makes a crash between the two writes harmless: the dispatcher commits the job `accepted`, with its result, first; then it appends the line, skipping it when a line for the same (`exp`, `i`, `run`) is already there; and at start it reconciles every active experiment's results file with the database (an accepted job with no line gets one, a line whose job is not accepted is removed). A crash between the commit and the append therefore leaves exactly one line after the restart.
- **The ratings** read the results files as before (only accepted lines are there), and their cache, keyed on the files' signature, recomputes after any append or rewrite.
- **The ledger:** each completed run writes one `cpu` event when it completes, through the ledger's writer: `activity = lab:<exp>:<i>`, `activity_kind = lab`, `task_class = cpu`, `machine_id` the executor's row, `provider_id` its owner (null for the host), `consumer_id` the job's owner for a primary run and null for a replica or tiebreak (verification is the server's own work, given by the machine's owner and used by nobody), `cpu_core_s = min(reported cpu_s, observed wall × 1.05 + 1, 1.5 × reference)`, where `reference` is the job's reference cost (the cost table's `cpu_s`, P4.5.4, or the replica's own `cpu_s` when the job was replicated). The seconds are the helper's own report, so they are bounded twice: by what the server observed (a game is one thread; `flags.overreported_cpu` past it, which no honest helper can reach and which blocks promotion), and by the work itself (`flags.capped_cpu` past 1.5 × the reference: a CPU job is worth at most 1.5 times what it costs a reference machine, however long it is held or however slowly it runs; informational, since a slow honest machine reaches it too). The rate per core-second is still the machine's CPU class's (3-10); a machine's measured speed (`trust.speed`: the median of reference over its own `cpu_s` on its replicated jobs) is shown beside its class to administrators, and `flags.class_suspect` is set when it is under half the median speed of the other measured machines of its class, for an administrator to pin its class (`class_override`). `verification` is `pending` until the job settles, then `verified` (matched, or the host's), `unverified` (accepted without a replica) or `rejected` (credits set to 0, the hour's rollups recomputed, and any budget settlement it made reversed). `ingest_lab` and its reading of the results files go. A job admitted under a grant with a budget settles its primary run's credits into that budget as a model step does (3-10's keeper, through the ledger's writer), and admission checks the budget before each offer, so a hard budget stops CPU work at its limit.
- **Power rows** from helpers' `power` frames are written as the host's sampler writes its own (`usage`), so costing prices a helper machine's measured energy; the KNOWN_ISSUES item narrows to machines whose power cannot be read.

### P4.5.8 Trust tiers: replication, sampling, promotion, quarantine, withdrawal

**Settings** (`settings_kv.verification`, admins; defaults from plan §1 where it gives them): `new_streak` 5, `provisional_rate` 0.10, `trusted_rate` 0.02, `promote_verified` 50, `overreport_days` 30, `new_per_owner` 2, `new_verify_share` 0.5.

**Verifiers.** Only the local executor and machines an administrator marked `verifier` (`trust.verifier`, on a `trusted` machine) run replicas, and only matches against them count toward `streak` and `verified`. A `new` machine's replicas run on the local executor only. A trusted machine of another owner is not enough: one person with two accounts could have their trusted machine vouch for their fake one.

**The rules,** held by `citar/jobs/trust.py` and its table-driven tests:
1. **Replication is decided, and the replica created, only after the primary's result is committed.** On committing a primary's signed `job_result`, the dispatcher replicates the job always for a `new` machine, and for a `provisional` or `trusted` one when `blake3(server secret ‖ job id)`, read as a fraction, is below `provisional_rate` or `trusted_rate` (the machine's tier when the result arrived). Only then is a replica created and offered. Nothing about a primary's offer or run differs between sampled and unsampled jobs, and no replica exists while the primary is in flight, so a helper cannot learn which of its jobs will be checked before it has answered. If the primary fails, the job is simply re-queued. Runs on the local executor are never replicated.
2. **Visibility:** replicas, tiebreaks and the `settling` state are shown only to administrators until the job settles. To everyone else (the experiment's owner and viewers, the machine's owner) a job is `done` from the moment its primary's result is committed, in `GET /api/lab/jobs`, `GET /api/machines/{id}/jobs` and the Queue and Lab pages; once it settles they see the accepted run and its verification badge. What a helper's owner learns then is about a result already given.
3. **Load on the verifier:** a `new` machine is offered work only while its owner has fewer than `new_per_owner` other `new` machines with work in hand (a third waits); replicas of `new` machines take at most `new_verify_share` of the local executor's runs while other work waits (with one thread, every other run), the rest going to its own and to sampled work. A `new` machine whose replicas cannot be placed gets no more offers until they can (the Lab page says "waiting for a verifier").
4. **Settling a job:** with no replica, the primary's result is accepted (`unverified`). With one, the job is accepted when both match (spec hash, jobs build, result hash, chain head and rounds): `verified`. A replica that fails is re-offered: an infrastructure failure says nothing about the primary.
5. **A mismatch** against the local executor quarantines the primary's machine. Against a remote verifier, a tiebreak runs on the local executor, and every machine that disagrees with it is quarantined (a verifier can be wrong too). The verdicts and their evidence, kept on the run and the machine:
   - `result`: same chain, different result. A correct engine of one jobs build cannot produce it, so the evidence reads "tampering or an incompatible build" (the self-check makes the second unlikely, P4.4.3).
   - `chain`: the first round where the digests differ; worded as hardware or an incompatible build.
   - `signature`: a signature that does not verify against the registered key.
   - `chain_inconsistent`: digests that do not fold to the claimed head.
   - `claim`: a claim naming another job, run, machine, spec or jobs build, or a second result for a settled run with other hashes.
6. **Promotion:** each verified match against a verifier adds to `trust.verified` and `trust.streak`. `new` with `streak >= new_streak` becomes `provisional`; `provisional` with `verified >= promote_verified`, no mismatch, and no `flags.overreports` or `flags.overreported_cpu` in the last `overreport_days` becomes `trusted`. Each change writes an audit row (`server.trust`, actor `system`).
7. **Quarantine:** the machine gets no CPU job, and admission refuses it for any purpose but its owner's own use (code `quarantined`): a machine that returned a wrong game is not relied on for anyone else, its LLM work included. Its running runs are aborted and re-queued. A **tampering verdict** (`result`, `signature`, `claim`, `chain_inconsistent`) also sets the owner's `users.trust_tier` to `quarantined`: every machine of that owner is refused CPU work, and a newly registered row starts nowhere, until an administrator releases the owner. A `chain` verdict quarantines the machine only. A key reset never changes `trust`.
8. **Withdrawal:** on any quarantine, every `unverified` accepted result the machine produced since `trust.since` (its registration, or its last release from quarantine) is withdrawn, not only those after its last verified match: a matched replica proves only its own job, and a selective cheater is honest exactly when it guesses it is watched. Each withdrawn job's line leaves the results file, its run's event becomes `rejected` (credits 0, rollups recomputed, any budget settlement reversed), the job is re-queued to run elsewhere, and the ratings recompute. The evidence lists the withdrawn jobs, and words a `chain` verdict as hardware and a tampering verdict as tampering or an incompatible build.
9. **A verifier quarantined:** every job it verified (its replica or tiebreak runs that matched) returns to `unverified` and is queued for a fresh replica on the local executor; every machine whose promotion counted its matches loses those matches and, if it falls below its tier's threshold, returns to `new`.
10. **Administrators** can set any tier, mark a trusted machine `verifier`, release a machine (back to `new`, counters reset, `since` now) or an owner (the existing user administration's `trust_tier`) from quarantine, withdraw by hand when quarantining (`withdraw: true`), and ask that a machine's next N jobs be replicated (`POST /api/admin/machines/{id}/replicate`).
11. **LLM work** stays attributed, not re-verified (C2): its events carry `flags.tier`, the machine's tier when the step ran; over-reporting blocks promotion (rule 6) but does not quarantine. **Model results from helper machines** (benchmark games, probes, the diplomacy leaderboard's games) count toward the global leaderboards only when their machine was `trusted`, a site machine, or owned by an administrator when they ran; the others are listed with an "unverified machine" badge and left out of the global boards until an administrator trusts the machine. An LLM-only machine has no CPU jobs to be promoted by, so its owner asks an administrator, who can judge it by its results.

**Reading plan §6.7's "only verified or trusted results feed lab results, ratings and pooled data":** this design counts a `provisional` machine's unsampled results (rule 4), with rule 8 taking them all back if the machine is ever caught. The strict reading would keep 90% of a provisional machine's work out of the lab until it reached 50 verified jobs, which at a 10% sample is about 450 jobs: the work would be wasted or held for hours. With withdrawal back to the machine's registration, a cheater gains nothing: everything unverified it ever contributed leaves the lab, the ratings and its credits, and its owner is refused CPU work. For model work, rule 11 is the same sentence's reading ("pooled data" taken as the global leaderboards). Both readings are one owner question for confirmation.

### P4.5.9 The update relay

The Servers page shows each helper's version, the latest signed one, and its `update_status`.

## P4.6 Threat model

**Assets:** a lender's machine (its CPU, memory, GPU, files, network, the API key a helper may front, its uptime); the server's data (lab results, ratings, the ledger and credits, model scores); members' accounts and the machines they own; the update channel.

**Actors:** (A) a malicious or compromised CITAR server, or its operator, against lenders; (B) a malicious lender or a modified helper against the server's data; (C) a broken but honest machine (bad RAM, an overclock, a denormal-flushing environment); (D) a network attacker between the two; (E) an attacker on the release channel (a compromised GitHub account or workflow); (F) another member against a machine they were not lent.

| Threat | Mitigation | Left over |
|---|---|---|
| A makes the helper run code, read files or reach the lender's network | No command, script or code is ever accepted; jobs are a closed vocabulary of typed, bounded specs running only compiled-in engine and bots (P4.4.1); completions go only to the configured endpoint with whitelisted parameters and the model allowlist; nothing reads outside the home | A bug in the engine or a spec parser on hostile input: specs are fuzzed with the frames (4-01), and the job host runs under limits |
| A exhausts the lender's machine | CPU lending is off until the lender turns it on at the machine; the local ceiling caps every figure (local always wins); hard limits where the OS allows, soft and labelled where not (P4.3.6); local quiet hours; `yield_to_llm`; spec bounds and deadlines | macOS limits are soft; a lender who needs hard limits there sets fewer threads |
| A pushes malicious or old code as an update | Manifests are verified against public keys compiled into the helper, whose secrets the server never holds; no downgrade; sha256 and size checked; https only, redirects included; the staged binary self-tests; policy `off`/`notify` locally (`notify` in packaged builds) | The release key itself (E) |
| A learns more about the lender than it should | Hardware reports can be a file or nothing; power off locally; the key's secret never leaves | The prompts a lender's model serves are seen by the lender, as in 0.1.5: lending a GPU means seeing what it computes |
| B fakes results or poisons the ratings | Every result is a signed claim bound to its run, machine, spec and jobs build; chains and result hashes recomputed by the server; replication of every job of a `new` machine and samples after, decided only once a result is in and invisible to its owner until settled; verifiers only the server and administrator-marked machines; quarantine on any mismatch, of the owner too on tampering; withdrawal of everything unverified since registration or release; quarantined machines serve nobody else | A patient cheater on a `trusted` machine contaminates about 50 jobs on average (2% sampling) before it is caught; all of them are withdrawn when it is |

| B steals another machine's identity | Tokens hashed at rest and revocable; keys bound on first use and resettable only by the owner or an admin; the rate limit before any lookup, counting distinct tokens | A token stolen before the real helper's first hello registers the thief's key; the fingerprint on the Servers page shows it, and a reset fixes it |
| C produces honest wrong results | The canary refuses jobs where denormals are flushed or read as zero, and the self-check where the golden job comes out differently; otherwise the same machinery as B, with evidence naming the round and worded as hardware, and the machine's owner not quarantined for a `chain` verdict | — |
| D reads or alters traffic | TLS with the OS verifier; `--insecure` only for loopback and private hosts; `--ca-file` for self-signed servers | — |
| E signs a malicious release | Phase 5's custody decision (offline key, or a protected environment with a required reviewer); two key slots for rotation; attestations | The owner's key management |

## P4.8 Decisions taken in this design

1. **v1 is refused, with a message a 0.1.5 helper prints, and a v2 helper waits for an old server** (P4.2.8); no transition window, and the hub carries exactly one protocol at every merge (P4.11).
2. **One WebSocket path**, `/ws/worker`, for both the refusal and v2.
3. **Additive within v2; job specs closed** (P4.2.1).
4. **Raw completions; one parser on the server** (P4.5.2); `json` mode's protocol prompt built by the server.
5. **Streaming between the helper and its endpoint, for cancel;** one `done` to the server.
6. **Cancel is acknowledged;** draining only for an unacknowledged cancel, flagged.
7. **Settings are acknowledged with what is in effect;** the scheduler and dispatcher read the acknowledgement.
8. **Rate limit before lookup, hop-aware address, `last_ip` written** (defects of P4.0).
9. **Machine keys are trust-on-first-use per row,** resettable by the owner or an admin without changing the machine's trust; owner-only on disk (0600, or an owner-only DACL), refused at start otherwise; signing in the helper's parent process, never in the job host.
10. **A shared `citar-jobs` crate** holds everything both sides must compute identically: specs and hashes, the lab result, the chain, claims and signatures, the update manifest, the job host and its limits.
11. **The kinds:** lab, ranking and reference games; ranking and reference are admins' `collection` experiments; reference results are baseline lines.
12. **Crashes are results:** final, verified like any other, never retried; a job never runs under a wall-clock budget, so a deadline is a failure and never a result.
13. **One job host process per executor,** applying its limits to itself, used by the helper and by the server alike; no orphans (stdin EOF ends it); a canary and a golden self-check before any job; memory counted per run; a host of another jobs build refused.
14. **Limits per OS** as P4.3.6's table, each reported hard or soft and shown.
15. **`yield_to_llm`** pauses a helper's games while its model works; no CPU job offered while a benchmark lease is live on the machine.
16. **The dispatcher lives in the server process;** `citar lab run` is retired; the host's machine row is the local executor and its settings replace the lab's worker counts.
17. **The local executor is trusted by definition** and verifies every `new` machine; otherwise only machines an administrator marked `verifier` verify, so no owner can vouch for their own machines through a second account.
18. **Sampling is keyed by the server's secret and decided after the result is in;** replicas are invisible to non-administrators until the job settles; trusted machines are still sampled at 2%.
19. **Provisional results count, with withdrawal on quarantine of everything unverified since registration or release** (P4.5.8; an owner question confirms the reading, and rule 11's for model results).
20. **Quarantine stops a machine's work for anyone but its owner,** CPU and LLM alike; a tampering verdict quarantines the owner too; release returns a machine to `new`.
21. **Ledger events are written per run** with `pending` until settled; replicas are given by their machine's owner and used by nobody; CPU seconds are bounded by observation and by 1.5 times the reference cost; rejected runs earn nothing and reverse their budget settlements; `ingest_lab` goes.
22. **Updates follow the server's own version,** relayed and verified by the server, verified again by the helper, never downgraded, applied when idle and handed off by a supervisor that rolls back; `notify` only in packaged builds; no key ships in Phase 4.
23. **Services:** per-user by default (systemd user unit, LaunchAgent, HKCU Run entry with its own supervisor), a real Windows service (a virtual account, a locked-down home) and a system unit on request with elevation done by the owner; exit codes 0, 75 and 78, and no exit at all on a permanent refusal in service mode.
24. **Test features** (`test-faults`, `test-update-key`, `test-jobs`) and the development guard (`dev-guard`) never ship (xtask) and confine a build to loopback; `dev-guard` also demands an explicit `--home`.
25. **The Linux release builds stay glibc-based** (on ubuntu-22.04, as today's helper), with rustls and the platform verifier, so TLS no longer depends on where a distribution keeps its CA bundle.
26. **The Python worker is deleted,** with its extra, its script, the wizard's flow and the install scripts' paths replaced by a pointer to the helper.
27. **Release names are unchanged** plus `citar-helper-macos-x64`; 4-14 switches release.yml's helper job to cargo with those names and a test holds helper.js to them; the rest of the release is Phase 5's.
28. **QA runs the server in WSL** for the cross-OS remote experiment, so no Windows listener ever leaves loopback.
29. **Jobs have their own compatibility key,** `jobs_build`, covering the runner, the jobs crate and the build flavour (P4.4.5).
30. **CPU lending is off on the machine until its owner turns it on there,** and a grant lends CPU only when it lists `lab`; administrators' own experiments need grants like anyone's.
31. **The protocol acknowledges results, expires offers and silent runs, and backs off re-offers;** a lost connection cancels the helper's completions.

## P4.9 Risks

1. **A target computes another game.** The engine's matrix holds today; the `jobs` set adds the job runner to it on five targets in both profiles, WSL checks it locally, every job host plays the shortest golden job before taking work (a machine that computes it differently is `unverifiable`, never quarantined), jobs are compared only within one jobs build, and a mismatch between honest machines that slipped past all that would show as a quarantine with "chain parted at round R", which the evidence makes diagnosable. Mitigation for an outbreak: an admin can release machines and set the rates to 1.0 while it is investigated.
2. **OS limit APIs** (Job Objects, cgroup delegation, macOS's lack of hard caps). One small `unsafe` module with SAFETY comments; each limit measured by a test; soft limits reported as soft, never claimed hard.
3. **The update channel.** Signatures, no downgrade, self-test, rollback; no key until the owner decides custody.
4. **Verification load on a one-vCPU VPS.** New machines double their work until five matches, and their replicas run only on the host, which verifies at 1 thread by default; at most two new machines per owner get work, and new machines' replicas take at most every other run of the host's while other work waits; admins can mark trusted machines `verifier`; "waiting for a verifier" is visible rather than silent.
5. **WSL networking.** Localhost forwarding from Windows into WSL is assumed and probed; the fallback topology is defined (P4.7.6).
6. **LM Studio's behaviour on a closed stream.** Measured, not assumed: the cancel check compares a following request's latency with the same run's baseline.
7. **A helper newer than its server** (updated elsewhere), or built in another profile: LLM work goes on (same protocol); CPU jobs are not offered across jobs builds until the two match, and the Servers page says so.
8. **This laptop throttles** (P3.9.7): timings within a run only; limits checked as upper bounds.
9. **Fifteen packages in sequence.** Each sized like a Phase 3 package or smaller; the two at the upper bound (4-05, 4-09) name where to split, and the proof of work is split in two (4-11, 4-12) from the start.
